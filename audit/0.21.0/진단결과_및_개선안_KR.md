# Burp Workbench KR 0.21.0 — 커뮤니티 실전 흐름 평가

작성: 2026-10-11 (한국 시간) / 대상: 저장된 개발 패키지의 배포 JAR, Community Security Lab 3.4.0

## 결론

현 버전은 계정별 인가 비교, SQL 오류·참거짓 후보 탐지, 반사 XSS 후보 확인, 활동 현황과 증거 묶음을 연결하는 진단 보조 도구로 사용할 수 있습니다. 이번에 가장 명확하게 재현한 수정 후보는 **기대 권한 매트릭스가 이미 확보한 소유자 재조회 근거를 덮어쓰는 문제**입니다. 계정 역할·조직이나 입력값이 달라져도 완료 상태가 유지되는 점, 업무 증거가 요구 조합 전체를 보장하지 않는 점도 운영상 보완할 가치가 있습니다.

확장 구현 소스와 JAR, 사이트 운영 소스와 WAR는 변경하지 않았습니다. 별도 진단 하네스와 결과·증거만 추가했습니다. 기존 사이트에 충분한 취약/수정 대조 경로가 있어 이번에는 운영 기능을 추가할 필요가 없었습니다.

## 이번에 실제 수행한 범위

| 구분 | 결과 | 의미 |
|---|---:|---|
| 기존 전 기능 HTTP 하네스 | 100개 검사 / 199건 요청 | 배포 JAR, 9개 기능군, 16개 페이로드 프로필; 개별 프로필의 일부는 제한된 응답 fixture |
| 이번 커뮤니티 진단 하네스 | 65개 검사 / 118건 요청 | 취약·수정 비교, 저장된 결과 읽기, 실제 권한 비교 패널 로직, 증거 ZIP·완료 상태 |
| 합계 | **165개 검사 / 317건 요청** | 최종 실행끼리 합산; 준비·초기 실패·이전 대화의 실적은 제외 |
| 운영 파일 무변경 확인 | 129개 일치 | 확장·사이트 소스, JAR, WAR의 실행 전후 SHA-256 비교 |
| 서버 종료 | 확인 | 임시 서버 종료 및 18299 포트 닫힘; 기본 하네스도 서버 종료 |

실행 방식은 **실제 loopback HTTP + Spring/Tomcat/H2 서버 + 0.21.0 배포 JAR + API 어댑터/헤드리스 Swing**입니다. 이번에 Burp 본체, 화면 클릭, 브라우저 DOM 실행, Docker/Oracle/Nginx, 외부 BApp 또는 Pro Collaborator를 새로 실행한 것은 아닙니다. 이전 대화의 Burp/브라우저 검증을 이번 숫자에 포함하지 않았습니다.

검사 통과는 관찰한 조건이 기대와 일치한다는 의미입니다. 의도적으로 취약한 사이트가 안전하다는 뜻이나, 모든 버그가 없다는 뜻이 아닙니다.

테스트 대상 JAR SHA-256: `22a9c4248b272bcedea7cd7c5e1f3fbe5c9bc26924d72907fc53148408d6bbac`

사이트 WAR SHA-256: `6b325934133adac02ef28c1745b1cfb48a598985171ed3393f6f6df0af491301`

초기 실행은 관리자 응답의 필드명을 소문자 `email`로 기대한 테스트 오류 때문에 중단됐습니다. H2 응답의 대문자 필드와 무관하게 실습용 이메일 값으로 확인하도록 **진단 하네스만** 수정했습니다. 초기 기록은 `initial-run/`, 최종 결과는 `results/`입니다.

## 커뮤니티에서 확인한 공격과 영향

아래 경로의 `{mode}`에는 `vuln` 또는 `fixed`가 들어갑니다. 모든 요청은 격리한 실습 서버에만 보냈습니다.

| 항목 | 재현 방법과 실제 영향 | 취약 경로 | 수정 경로 | 확장 활용 |
|---|---|---|---|---|
| 비공개 게시글 열람 | Bob 소유 `/posts/102`를 Alice로 조회; `BOB_PRIVATE_NOTE` 확인 | 200, 본문 노출 | 404, 소유자 재조회 200 | OWNER_ONLY + `$.OWNER_ID`로 타인 객체 후보 확인 |
| 비공개 쪽지 열람 | `/messages/202`를 Alice로 조회; Bob→Admin 내용 확인 | 200, 본문 노출 | 404 | 읽을 권리가 없는 계정에는 DENY 설정. 수신자도 정당한 독자이므로 발신자 필드 하나를 전역 소유 정책으로 쓰지 않기 |
| 첨부파일 노출 | `/files/bob-private-file`을 Alice 및 비로그인으로 조회 | 양쪽 모두 200, `BOB_PRIVATE_ATTACHMENT` 노출 | 양쪽 모두 404 | 다운로드 응답 비교 후 본문·해시 확인 |
| 관리자 API 우회 | Alice로 `/admin/users?role=ADMIN` 요청 | 200, 계정·역할·이메일 반환 | 403 | 계정별 기대 권한 DENY와 성공 응답 대조 |
| 타인 글 수정·삭제 | Bob의 임시 비공개 글에 Alice로 쓰기; 소유자로 재조회 | 수정 200 후 내용 변경, 삭제 200 후 404 | 수정·삭제 403, 원본 유지 | 쓰기 허용을 명시한 뒤 변경 전후 상태를 업무 흐름과 함께 확인 |
| 검색의 접근통제 누락 | 비로그인으로 `/search?q=` 요청; SQL 구문 없이 확인 | 비공개 본문 반환 | 비공개 본문 없음 | SQLi와 별개 근본 원인의 접근통제 이슈로 분리 |
| SQL 삽입 | 검색에 작은따옴표 및 일치하는 참/거짓 쌍; 고정·적응형 각각 실행 | SQL 오류 후보 및 조건 차이 후보 | 두 종류 후보 없음 | Repeater 재현과 기준 응답을 함께 보관 |
| 반사 XSS 후보 | `/vuln/preview`와 `/fixed/preview`의 동일 입력 대조 | XSS 반사 후보 | 문자 반사/인코딩 관측 | HTML 반사와 브라우저 실행을 구분 |
| 저장형 XSS 연결 | 댓글 저장 뒤 별도 GET에서 onerror 포함 마커 확인 | 저장·조회 확인; 단일 요청 페이로드 엔진은 반사 XSS로 표시하지 않음 | 이번 전용 하네스에서는 DOM 실행 대조 안 함 | 기존 저장/조회 마커 기능을 사용하고 브라우저 실행 증거를 별도로 연결 |
| 활성 콘텐츠 업로드 | Bob의 임시 글에 `.html`, `text/html`로 업로드 후 비로그인 다운로드 | 수락 200, HTML·inline·본문 반환 | 415 거부 | 업로드 수락만 보지 말고 다운로드 MIME·Disposition·권한까지 확인 |
| CSRF 토큰 강제 | 로그인 쿠키만 두고 토큰 없이 본인 글 수정 | 200 | 403 | 토큰 누락 허용은 확인. 실제 교차 사이트 브라우저 공격 성공은 이번 결과로 단정하지 않음 |

이 사이트는 학습용 취약 구현을 포함합니다. 위 결과를 새로 발견한 외부 서비스 취약점이나 실제 버그바운티 보상 대상이라고 표현할 수는 없습니다. 재현된 접근통제 문제는 외부 진단에서 개인정보 열람·무단 변경 같은 영향으로 검증할 수 있는 유형입니다.

## 수정·개선 우선순위

### 1. 소유자 재조회 근거 보존 — 수정 권장, P1

실제 `AuthComparePanel`로 Bob의 비공개 글을 Alice에게 재전송했습니다. 두 실행 모두 대상 404 후 Bob 재조회 200을 확인했고, 각 실행에서 실제 HTTP 요청은 2건이었습니다.

- 기대 권한 매트릭스 없음: `은닉형 접근 차단 후보 · 소유자 재조회 2xx 동일 · 대상 HTTP 404`
- 같은 경로를 Alice DENY로 설정: `기대 DENY · 404/410 존재·세션 재검토`

`AuthComparePanel.execute`의 매트릭스 후처리가 앞 단계의 존재 확인 정보를 받지 않는 `BountyMatrix.assess` 결과로 표시를 대체합니다. 안전하지 않은 접근을 허용하는 버그라기보다, 근거가 손실되어 이미 확인한 차단을 다시 검토하게 만드는 판정 일관성 문제입니다.

**제안:** 매트릭스 판정에 기준 응답·소유자 재조회 성공·대상 상태를 전달하고, DENY+404+동일 객체 재확인일 때 차단 근거를 유지합니다. 재조회 실패·본문 변동·삭제 가능성은 계속 보류합니다. ALLOW인데 404인 경우는 별도의 정책/세션 재검토를 유지합니다.

**수용 조건:** 위 두 실행의 존재 확인 근거가 모두 남고, ALLOW/삭제/세션 만료/동적 응답의 음성 사례를 구별할 것.

### 2. 계정 역할·조직 변경 시 완료 재검토 — 개선 권장, P1

Alice·Bob 두 요구 조합을 완료한 업무에서 Alice의 **확장 메타데이터**를 USER/A → ADMIN/OTHER_ORG로 변경해도 업무는 `업무 완료`를 유지했습니다. 실제 서버 계정의 권한 변경을 이번에 수행했다는 뜻은 아닙니다.

**제안:** 이름 변경은 이력을 유지하되, 역할·조직 변경은 판정 조건의 새 버전으로 취급해 관련 완료 업무를 재검토로 돌립니다. 이전 완료 시점의 역할·조직 스냅샷을 함께 보여주면 재점검 대상을 설명할 수 있습니다. 세션은 그대로인데 로그인 주체가 바뀌는 사례에는 선택적 `/me` 확인을 연결합니다.

### 3. 입력값·객체 범위와 완료의 관계 — 개선 권장, P1

같은 경로의 `lab_hidden=first`를 `second`로 바꾸어 관측했을 때 계정은 `점검 완료`, 업무는 `업무 완료`를 유지했습니다. 해당 입력 자체는 `미점검`으로 남았습니다. 현재 URL 완료와 입력 완료를 따로 관리하는 설계에서 나오는 동작입니다.

**제안:** 업무별로 엄격 완료 옵션을 두어 필요한 입력의 완료도 요구하고, 중요 입력값/객체 집합 변경을 감지하면 재검토합니다. 인증값을 원문 저장하지 않으면서 변경을 감지할 수 있는 설계가 필요합니다. 모든 검색어·페이지 변화마다 재검토하면 잡음이 커지므로 `id`, 조직, 소유자 등 사용자가 지정한 중요 입력 중심으로 적용하는 편이 좋습니다.

### 4. 계정×API별 증거 충족률 — 기능 강화, P1

요구 계정 2개인 업무에서 두 URL을 수동 완료한 뒤 **Alice 증거만 실제 ZIP에 저장**해도 업무를 완료할 수 있었습니다. 현재 안내에 명시된 “연결된 ZIP 1개 이상” 조건에는 맞지만, Bob의 결과를 증빙하지 않습니다. 파일이 현재 존재하는지 확인하는 기능도 코드상 없습니다. 파일 존재 검사는 이번에 실동작으로 검증한 기능이 아닙니다.

**제안:** `증거 있는 조합/요구 조합`을 표시하고, 업무별 최소 증거 요건을 선택하게 합니다. 저장 시 해시와 보관 위치를 남기고 재검증 버튼을 제공하되, 이동한 파일은 재연결할 수 있어야 합니다. 완료 뒤 실패한 업로드·유실된 ZIP을 정상 증거로 착각하는 일을 줄일 수 있습니다.

### 5. 저장형 XSS와 업로드를 기존 흐름에 연결 — 기능 강화, P2

저장/조회 마커 추적은 이미 있습니다. 단일 POST의 `{id: ...}` 응답에서 XSS 후보가 안 나오는 것을 미탐 버그로 단정하면 안 됩니다. 실제 위험은 별도 조회와 브라우저 출력에서 발생합니다.

**제안:** 기존 `StoredFlows`와 업무 흐름에 저장 요청 → 조회 요청 → 화면 출력 → 실행 확인의 단계를 연결합니다. 증거 수준을 `저장`, `조회`, `HTML 출력`, `브라우저 실행`로 나누고 자동 확정하지 않습니다. 업로드 역시 수락 → URL 추출 → 다른 계정 다운로드 → MIME/Disposition → 브라우저 동작 순서로 묶으면 실무 재현 과정이 짧아집니다.

### 6. URL 대표 선택과 정책 다양성 — 기능 강화, P2

공개 글 101과 비공개 글 102는 동일 `/posts/{ID}` 그룹이 됩니다. 이는 그룹화 자체의 오류는 아니며 원본 목록도 보존됩니다. 다만 소유자가 볼 때 둘 다 200이므로 상태 코드만으로 대표를 고르면 접근 정책의 차이가 충분히 드러나지 않을 수 있습니다.

**제안:** 대표 URL에 공개/회원/비공개·소유자·조직·역할 태그를 부여하고, 동일 200에서도 서로 다른 정책의 예시를 남깁니다. 현재 상태별 대표 선택 기능을 확장하는 방향입니다.

### 7. 제출 가능한 증거 패키지 보완 — 기능 강화, P2

실제 `BountyEvidence.save`로 요청·응답 ZIP을 만들고 세션 쿠키가 포함되지 않음을 확인했습니다. JSON은 본문 포함 옵션으로 남길 수 있지만 비 JSON/바이너리 본문은 텍스트 증거에서 제외됩니다. 다운로드 노출의 실제 내용이나 업로드된 HTML을 제출하려면 추가 자료가 필요할 수 있습니다.

**제안:** 사용자 선택에 따른 제한적 파일 증거, 민감정보 미리보기, 원본 바이트/가린 미리보기의 명확한 구분, 소유자 기준·타인 요청·수정 대조를 하나의 발견 건에 연결합니다. 여러 도구가 같은 현상을 발견할 때 하나의 근본 원인으로 묶되, 검색 인가 누락과 SQLi처럼 원인이 다른 것은 분리해야 합니다.

## 이번에 정상 동작한 부분 — 과거 개선안을 반복하지 않기

- PUBLIC 정책을 넣은 공개 글은 두 모드 모두 `공개/공유 허용`으로 처리됐습니다.
- 소유자 전용 비공개 글·쪽지는 취약 경로에서 타인 객체 접근 후보가 나왔습니다.
- 매트릭스 없이 소유자 재조회가 성공한 수정 경로의 404는 은닉형 차단 후보로 구별됐습니다.
- 고정·적응형 SQL 참/거짓 후보는 취약 경로에서 탐지되고 수정 경로에서는 나오지 않았습니다. 과거 정규화 미탐은 이번 재현에서 관측되지 않았습니다.
- Admin의 정당한 접근은 기존 계정별 매트릭스 ALLOW로 표현할 수 있습니다. 역할 매트릭스가 없다고 보아 새로 만들 필요는 없습니다.
- 인증값은 활동 저장 JSON에서 제외됐고, JSON 복원 후 인증 연결을 자동 복원하지 않았습니다.
- 실제 ZIP 생성 후에 증거 기록을 연결하는 기능을 사용했고, 내보낸 요청의 쿠키 가림을 확인했습니다.

## 사이트에 다음으로 추가하면 좋은 사례

현재 사례로 이번 평가를 끝낼 수 있어 다음 항목은 **제안만 했으며 구현하지 않았습니다**. 기존의 상태 코드·저장/조회·프로토콜 fixture를 재사용하고 중복 기능은 만들지 않는 편이 좋습니다.

| 추가 사례 | 확장에서 검증할 동작 | 실무 활용 |
|---|---|---|
| 조직 A/B와 동일 ID 구조의 게시물 | 조직별 기대 정책, 정책 변경 후 재검토 | SaaS 고객사 간 데이터 격리 진단 |
| 같은 세션 식별자를 유지한 계정/역할 전환 | `/me` 신원 확인, 이전 완료 무효화 | 세션 재사용·권한 변경 후 재점검 |
| 같은 경로·같은 200, 공개/비공개/공유 객체 | 정책별 대표 선택과 계정×객체 커버리지 | IDOR 샘플링 누락 감소 |
| 저장된 마커를 다른 계정의 화면에서 조회 | 저장·조회·DOM·실행 단계 연결 | 저장형 XSS 및 첨부 HTML 영향 평가 |
| 감사 로그가 있는 임시 글 생성→수정→삭제 | 응답 코드 외에 상태 변경·복구 확인 | 업무 로직과 재현 보고서의 신뢰도 향상 |

새 fixture는 loopback 전용 실습 모드와 초기화 기능을 유지하고, 취약/수정 쌍 및 허용·거부 기대값을 같이 제공하는 것이 좋습니다.

## 권장 개발 순서와 사용 흐름

1. **다음 패치:** 404 재조회 근거 보존, 역할·조직 변경 재검토. 재현된 상태 문제부터 수정합니다.
2. **다음 기능:** 업무별 엄격 완료·조합별 증거 충족률. 진단 누락과 완료 의미를 명확히 합니다.
3. **그다음:** 기존 업무 흐름·저장 마커·증거 저장을 연결한 발견 건 관리, 업로드 후속 조회, 브라우저 증거 연결.

현 버전으로 진단할 때는 SCOPE → Alice/Bob/Admin/비로그인 연결 → 공개/소유자 및 ALLOW/DENY 정책 설정 → 정상 탐색·JS/OpenAPI 수집 → 계정 교차 재전송 → 실제 본문/상태 변경 확인 → 증거 ZIP → 계정·업무 수동 완료 순서가 유용합니다. 쓰기 검사는 이번처럼 임시 객체를 만들고 소유자 재조회로 실제 영향을 확인하면 상태 코드만으로 성공을 과장하지 않을 수 있습니다.

## 결과 파일과 재실행

- `results/results.json`: 65개 검사, 권한 판정, 페이로드별 후보, 완료 상태 관찰.
- `results/audit.log`: 최종 진단 로그.
- `results/http-evidence.zip`: 소유자 기준·타인 요청·수정 대조·익명 검색·수정 후 소유자 조회의 가림된 증거 28건.
- `results/single-account-evidence.zip`: 두 계정 업무에 한 계정의 증거만 연결한 재현 자료.
- `results/integrity.json`: 실행 전후 무변경·JAR/WAR 해시·서버 종료.
- `baseline/`: 기존 100개 검사 결과 및 로그. 원본 JSON의 버전 표기는 예전 고정 문자열이므로 시험 JAR는 위 해시를 기준으로 식별합니다.
- `BountyAudit.java`, `run_audit.py`: 이번에 추가한 진단 코드. 확장 운영 코드가 아닙니다.
- `initial-run/`: 테스트의 필드명 기대 오류로 중단된 첫 실행 기록. 최종 통과 수에 합산하지 않습니다.

필수: 기존 개발준비 ZIP을 풀어둔 작업공간, 사이트 3.4.0, Java 17+ 컴파일러, Python 3.10+.

```bash
# 먼저 기존 하네스를 실행해 의존성과 테스트 API 어댑터를 준비합니다.
python3 /path/to/burp-workbench-workspace/dev.py http-test --port 18199

# 이 결과 패키지의 폴더에서 실행합니다. 빈 loopback 포트를 사용합니다.
```
