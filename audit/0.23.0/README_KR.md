# 0.23.0 커뮤니티 버그바운티 흐름 감사

2026-10-11에 확장 0.23.0의 실제 빌드 JAR와 커뮤니티 사이트 3.5.0의 현재 Java 소스를 사용하여 **266개 검사, 실제 HTTP 259건**을 수행했습니다. 모두 통과했고 격리 서버 포트 18399의 종료와 검사 중 운영 소스 불변을 확인했습니다. 최종 릴리스 시점의 재실행 결과와 JAR SHA-256은 `docs/VERIFICATION_0.23.0.json` 및 PR을 기준으로 확인하세요.

이 수치는 신규 감사만의 결과입니다. 기존 0.21.0 감사, 기본 회귀 검사, 기존 전체 기능 HTTP 검사의 숫자를 합쳐 기록한 것이 아닙니다. 266개에는 64개 생성 상한까지의 개별 성공 응답 확인도 포함하며, 모두 서로 다른 취약점 또는 GUI 동작 수라는 뜻은 아닙니다.

## 수행 범위와 발견 근거

| 시나리오 | 실제 확인한 결과 | 확장 활용 및 의미 |
|---|---|---|
| 공개·개인·조직 A/B·공유 객체 6종 × 5계정 × 두 구현 | 소유자 기준과 동일 객체 재조회, 기대 ALLOW/DENY에 맞는 200/404 또는 의도한 취약 200 | `BountyMatrix` 운영 판정과 PUBLIC 오탐 방지 확인. 동일 URL 형식·상태만으로 모든 정책을 대표할 수 없음 |
| 없는 객체·잘못된 모드 | 404, 유효한 소유자 기준이 없는 경우 재검토 | 단순 404를 안전한 차단으로 확정하지 않음 |
| 저장 → 소유자/타계정/비회원 조회 | vuln의 raw HTML/공개 조회와 fixed의 이스케이프/소유자 제한 | `StoredFlows`가 쓰기 성공·2xx 재조회·HTML 출력·문자 표시 후보를 분리. 브라우저 실행 증거는 비어 있음 |
| 업로드 → 다운로드 | vuln inline HTML, fixed TXT만 허용·text/plain·attachment, 다른 계정 404 | 같은 마커라도 MIME에 따라 HTML 출력 단계를 다르게 기록 |
| 삭제·초기화·입력 한도 | 타계정 삭제 거부, 소유자 삭제 후 404, CSRF/로그인 요구, 본문·파일 제한, 65번째 생성 429, 현재 계정 64개만 초기화 | 검증을 반복할 수 있고 다른 계정의 대조 데이터를 유지 |
| 기존 커뮤니티 SQL/XSS 대조 | 실제 H2 SQL 오류와 HTML 반사 후보는 vuln에서만 관측, fixed는 같은 후보 없음 | production `Adaptive`/`Engine`을 실제 HTTP 응답에 연결한 양성·음성 대조 |
| 증거 ZIP | 운영 `BountyEvidence`로 저장, 실습 쿠키·CSRF 제거 및 관측 마커 보존 | 재현 자료와 진단 근거를 함께 정리하되 세션 값을 내보내지 않음 |

사이트의 vuln 결과는 의도적으로 만든 교육용 취약점입니다. 외부 서비스에 제출할 유효한 버그바운티 제보 건수로 세지 않습니다. `<b>` 마커를 그대로 반환하는 것은 HTML 출력 관측이며 스크립트 실행을 증명하지 않습니다. 브라우저 실행·영향을 확정하려면 별도의 실제 브라우저 검증이 필요합니다.

## 변경 전후

- 기존 저장형 점검은 쓰기와 조회 관측을 한 줄의 상태로 해석하기 쉬웠습니다. 0.23.0은 단계와 원본 요청 연결을 분리하며, 이 감사는 실제 저장/조회 HTTP로 그 동작을 확인합니다.
- 사이트에 같은 경로 형식·HTTP 200을 쓰면서 공개/소유자/조직/공유 정책이 다른 객체를 추가했습니다. 대표 요청 하나의 성공 결과만 보고 다른 계정·조직을 완료하지 않도록 실습합니다.
- 업로드 성공 응답만으로 영향이 입증되었다고 보기 어려웠습니다. 별도 다운로드와 응답 MIME/Disposition, 교차 계정 접근을 함께 검사합니다.
- 임시 객체가 누적되는 점검 대신, 소유자만 정리할 수 있는 삭제/초기화와 상한을 제공해 동일 시나리오를 반복할 수 있습니다.
- 저장소의 기존 Compose는 과거 `dist/ROOT.war`를 복사하는 Dockerfile을 사용해 새 소스가 반영되지 않을 수 있었습니다. 현재 Compose는 `Dockerfile.source`로 현재 Java/리소스를 빌드하도록 수정했습니다. 실제 Docker 기동 검증은 수행하지 않았습니다.

## 재실행

```sh
python dev.py check
```

`check`는 최신 JAR를 빌드하고 기존 검사 다음에 이 감사를 수행합니다. 이미 빌드와 런타임 준비가 끝난 경우에는 별도로 실행할 수 있습니다.

```sh
python audit/0.23.0/run_audit.py --workspace . --port 18399
```

- 현재 버전은 `build_all.py`와 lab `pom.xml`에서 읽습니다. 과거 0.21.0 JAR나 `dist/ROOT.war`의 애플리케이션 코드를 실행하지 않습니다.
- 기존 HTTP 하네스가 준비한 런타임 JAR 전체의 SHA-256을 허용 목록과 비교하고, 현재 lab 소스를 새 폴더에 컴파일합니다.
- 서버는 loopback에서만 구동합니다. 포트가 사용 중이면 기존 서비스에 접속하지 않고 실패합니다.
- 실행 결과는 `.run/results.json`, `.run/integrity.json`, `.run/audit.log`, `.run/server.log`, `.run/http-evidence.zip`에 생성됩니다. `.run`은 Git 추적 대상에서 제외합니다. 중요한 최종 실행 근거는 릴리스 검증 폴더로 별도 보존합니다.
- 현재 실습 데이터·토큰만 사용하고 기존 Burp/브라우저/프록시 설정을 변경하지 않습니다.

## 이번 실행에 포함하지 않은 환경

HTTP 서버는 Spring MVC·임베디드 Tomcat·격리 H2(Oracle 호환 모드)입니다. 확장 알고리즘은 실제 JAR에서 실행하고 호스트 연동은 API 어댑터를 사용했습니다. 실제 Burp 설치 및 Docker 실행 명령은 이 작업 환경의 제한된 확인에서 발견하지 못했습니다.

실제 Burp GUI/네이티브 호스트, 브라우저 DOM/JavaScript 실행, 전체 Docker/Oracle/Nginx, Pro Collaborator 및 외부 BApp 검증을 수행했다고 표시하지 않습니다. 과거 환경의 실행 기록도 이번 결과에 합산하지 않습니다.
