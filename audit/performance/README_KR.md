# 수집·Mapper 성능 비교

동일한 합성 요청·응답을 개선 전후 소스에 넣어 작업량과 지연을 비교합니다. 운영 수집 콜백, 실제 디스크 저장소, Swing 타이머와 Mapper 코드를 사용합니다. Montoya 호스트는 테스트 어댑터입니다. 실제 Burp GUI, 브라우저, 네트워크 처리량 또는 다시간 내구성을 검증했다는 의미가 아닙니다.

## 실행

Java 17+와 각 확장의 `deps/*.jar`가 필요합니다. 기준 소스는 원하는 커밋을 별도 디렉터리에 준비합니다. 현재 소스를 수정하는 작업이 끝난 뒤 실행하세요.

```sh
python audit/performance/run.py \
  --baseline /absolute/path/to/baseline-repository \
  --candidate /absolute/path/to/candidate-repository \
  --dependencies /absolute/path/to/repository-with-deps \
  --output tmp/performance/comparison-1
```

`--component capture` 또는 `--component mapper`로 하나만 실행할 수 있습니다. 한쪽 소스만 주는 실행도 지원합니다. 컴파일 결과·로그·JSON은 지정한 출력 디렉터리에만 기록하며 저장소의 `build/`, `dist/`, 배포 파일을 건드리지 않습니다. 같은 컴포넌트에 기존 클래스가 있으면 덮어쓰지 않으므로 반복 실행에는 새로운 출력 경로를 사용합니다. 컴파일 도중 소스가 바뀌면 비교를 중단합니다.

결과에는 Java 버전, 힙 상한, Java 소스·하네스·의존성 SHA-256을 기록합니다. 외부 대상에 요청하거나 자격 증명을 사용하지 않습니다. 모든 입력의 호스트명은 `benchmark.invalid`입니다.

## 측정 항목과 판정

수집은 준비 운동 100건을 제외하고 네 시나리오를 실행합니다.

| 시나리오 | 입력 | 확인할 항목 |
|---|---|---|
| 작은 응답, 보통 속도 | 4KiB × 300건, 초당 100건 | 콜백·화면 반영 지연의 기준 |
| 작은 응답, 높은 속도 | 4KiB × 1,500건, 초당 500건 | 화면 대기열 증가와 전송 종료 후 배출 시간 |
| 큰 응답 | 64KiB × 600건, 초당 200건 | 복원·후속 분석·디스크 비용 |
| 버스트 | 4KiB × 1,500건, 속도 제한 없음 | 한꺼번에 들어온 수집의 화면 반영 |

콜백 시간은 콜백 호출 직전부터 반환 직후까지만 잽니다. 입력 속도를 맞추는 대기는 콜백 지연에 포함하지 않습니다. 화면 지연은 25ms 간격으로 별도 스레드가 Swing에 등록한 작업의 실행 지연입니다. 화면 전체를 그리는 비용은 포함하지 않습니다. 화면 대기 개수·가장 오래 대기한 항목 나이·힙 최대값은 표본이므로 실제 최댓값보다 작을 수 있습니다. 분석 대기열이 구현된 버전은 `captureObservations.pending()`도 기록합니다.

시간과 함께 **EDT의 패킷 복원 횟수**, **백그라운드 복원 횟수**, **테이블 행 삽입 이벤트 수**, **DefaultTableModel의 실제 행 벡터 개수**를 기록합니다. 모든 콜백·저장 원본·표시 행의 개수가 같고, 누락·오류가 0이며, 처음·가운데·마지막 패킷의 요청·응답 원본이 같은지 검사합니다. 새 인덱스/메타데이터가 디스크에 추가되면 `diskBytes`가 증가할 수 있습니다.

Mapper는 패킷 5,000개/15,000개와 기능 100개를 준비하고 기능별 패킷 조회를 30회 반복합니다. 반환한 멤버십 수와 패킷 ID 합을 검증하여 결과 누락으로 인한 가짜 가속을 막습니다. 별도 브라우저 상관관계 시나리오는 기존 패킷 600개·무관 URL 이벤트 40개·일치 이벤트 20개·무관 신규 패킷 200개를 사용합니다. 같은 요청이 하나 더 들어오면 모호해진 매핑 1개가 해제되는 것도 확인합니다. 후보 계측 API가 있는 개선 버전에서는 무관 URL의 후보 검사 증가가 0인지 확인합니다.

벽시계 속도 향상을 통과 조건으로 두지 않습니다. JIT·GC·호스트 부하·디스크 상태의 영향을 받으므로 동일 환경에서 반복한 값과 결정적인 작업량을 함께 해석해야 합니다. 힙 값은 사용 시점의 관측값이며 보존 메모리의 정밀 측정이 아닙니다. 인덱스 조회가 빨라져도 삽입 비용이나 디스크 사용이 증가할 수 있으므로 모든 결과를 함께 기록합니다. 실행에 따른 임시 원본은 확장 unload 또는 Mapper close 시 제거합니다.
