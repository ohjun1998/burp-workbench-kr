# 0.22.0 / 0.22.1 변경 및 테스트 안내

최신 테스트 배포는 **0.22.1**입니다. GitHub CI에서 기존 HTTP 하네스의 활동 큐 대기 경쟁 상태를 발견해, 큐에 완료 신호를 넣고 실제 처리 완료를 기다리도록 수정했습니다. 최초 0.22.0 파일은 그대로 보존합니다. 확장 기능은 동일하며 버전 표기를 갱신했습니다.

0.21.0 진단의 P1 결함과 완료 조건을 보강한 테스트 배포입니다. 현재 작업은 `account-a/0.22.0-review-and-downloads`에서 진행하며, main 병합 여부는 PR을 기준으로 확인합니다.

## 달라진 동작

| 대상 | 이전 | 0.22.0 |
|---|---|---|
| DENY + 404/410 | 매트릭스가 소유자 재조회 근거를 덮어씀 | 같은 대상·인증의 소유자 재조회가 2xx이고 본문이 같으면 차단 근거 유지 |
| ALLOW + 404/410 | 존재·세션 재검토 | 재조회 근거를 남기면서 정책·세션 재검토 유지 |
| 역할·조직 변경 | 계정/업무 완료 유지 | 관련 완료 계정/API와 업무를 재검토로 전환. 이름만 바꾸면 유지 |
| 완료 조건 기록 | 완료 시각 | 역할·조직·인증 연결 유무 스냅샷 추가. 실제 신원의 자동 증명은 아님 |
| 입력 완료 | URL과 별도, 업무 조건에 미반영 | 업무별 ‘모든 입력 수동 완료 필수’ 선택 가능 |
| 중요 입력값 | 변경 후 완료 유지 가능 | 사용자가 지정한 `URL:id`, `BODY:ownerId` 등의 변경·삭제 시 재검토 |
| 계정×API 증거 | ZIP 하나면 업무 조건 충족 | 모든 요구 조합에 파일 확인 증거를 요구하는 옵션과 충족률 표시 |
| 파일 상태 | 저장 기록만 보관 | SHA-256 확인, 재검증, 이동한 ZIP 재연결 지원 |

## 사용 순서

1. 기존 Workbench 확장을 해제하고 `downloads/extensions/0.22.1/`의 JAR를 로드합니다.
2. 활동 추적 → 업무별 현황 → 업무 설정에서 필요한 완료 조건을 선택합니다. 기존 업무의 옵션은 기본적으로 유지됩니다.
3. 중요 입력은 위치와 이름을 쉼표로 구분합니다. 예: `URL:id, BODY:ownerId`. 페이지·검색어 등 중요하지 않은 입력은 지정하지 않아 변경 잡음을 줄일 수 있습니다.
4. 조건 설정 후 정상 요청을 한 번 관측해 기준을 잡고, 계정별 URL/입력을 검토해 완료합니다. 기존 완료 기록에 중요 입력 기준이 없으면 첫 관측 시 재확인을 요구합니다.
5. 계정을 연결한 증거 ZIP을 저장합니다. ‘파일 확인 조합 / 요구’는 파일 확인이 끝난 증거가 있는 계정×API 수입니다. ZIP 한 개에 여러 계정의 증거가 있으면 해당 조합들을 함께 충족합니다.
6. 파일 이동 후에는 ‘증거 ZIP 재연결’로 동일 SHA-256 파일을 선택합니다. ‘증거 재검증’으로 등록된 파일의 삭제·변조를 검사하고, ‘증거 파일 확인’에서 결과를 확인합니다.
7. JSON을 다시 불러오면 파일 경로와 확인 상태는 자동 복원하지 않습니다. 필요한 ZIP을 명시적으로 재연결합니다. 엄격 증거 업무는 그동안 재검토로 표시됩니다.
8. 계정 URL을 재완료해도 업무는 자동 마감되지 않습니다. 업무 전체를 확인한 후 다시 완료하세요.

입력값과 인증값은 내보내지 않습니다. 중요 입력의 비교 해시는 메모리에서만 유지되므로 재시작 후 다시 기준을 확인합니다. 파일 상태는 마지막 확인 시점의 결과이며 백그라운드 파일 감시가 아닙니다. 중요 마감 전에 ‘증거 재검증’을 실행하세요. 파일 읽기/해시 검사는 작업 큐에서 수행합니다.

기존 ‘ZIP 1개 이상’ 옵션은 저장 이력 기준의 호환 동작입니다. 현재 파일 확인까지 요구하려면 ‘모든 계정×API의 파일 확인 증거 필수’를 사용하세요. SHA-256 일치는 파일 무결성 확인이며 증거 내용이나 진단 결론을 자동으로 검증하지 않습니다. 역할 변경 후 과거 증거의 적절성은 수동으로 다시 검토해야 합니다.

## 배포와 재생성

- [다운로드 목록](../downloads/README.md)
- `python dev.py release`: 빌드·기존/신규 회귀·loopback HTTP 검사가 성공한 후 버전별 파일 생성
- `python tools/package_downloads.py --verify`: 다운로드 해시와 현재 소스 대응 검증
- 같은 버전의 내용이 달라지면 덮어쓰기를 거부합니다. 확장은 `build_all.py`와 Java 표시/증거 버전 및 HTTP 하네스를 함께 변경하고, 실습 사이트는 `pom.xml` 버전을 올린 뒤 생성하세요.
- JAR는 고정 ZIP 시각과 정렬된 항목 순서를 사용합니다. JDK 버전 변경에 따른 바이트 차이까지 동일하다고 보장하지는 않습니다.
- 생성한 `downloads/`를 소스 변경과 함께 작업 브랜치에 커밋하고 PR로 올립니다. CI는 소스가 달라졌는데 다운로드를 갱신하지 않은 경우 실패합니다. 검증된 JAR와 로그도 Actions 아티팩트로 제공합니다.

Docker 패키지는 사이트 3.4.0 소스와 Compose·Windows/Linux 실행 스크립트를 포함합니다. Docker 안에서 WAR를 빌드하며, Docker Desktop 설치 파일이나 사전 빌드 이미지가 아닙니다. 첫 실행은 인터넷 연결이 필요합니다. 현재 저장소의 소스를 사용하며 이전 개발 패키지의 WAR를 배포물로 복사하지 않습니다.

## 검증 범위와 후속 항목

현재 실행 결과는 `VERIFICATION_0.22.0.json`과 PR에 기록합니다. 과거 0.21.0 검증 수치는 이번 검증으로 합산하지 않습니다.

이번 환경에는 Docker와 실제 Burp 설치가 없습니다. 실제 Burp 장시간 JS 수집/화면 흐름, Docker·Oracle·Nginx 전체 기동, Pro Collaborator 및 외부 BApp은 미검증입니다.

P2 후속 개발은 별도입니다: 저장형 XSS/업로드 단계별 발견 건 연결, 정책별 대표 URL, 바이너리 증거/민감정보 미리보기, Passive·데이터 비교의 원본 패킷 증거 연결. 최신 화면을 반영한 PDF와 실제 로그인 주체 자동 확인도 아직 완료하지 않았습니다.
