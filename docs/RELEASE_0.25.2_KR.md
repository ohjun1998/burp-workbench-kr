# 0.25.2 — 트래픽 건수·패킷 크기 제한 제거

요청·응답 목록의 최근 250건 보관 제한, 요청+응답 합계 128KiB 제한, 수집 대기열 250건 제한을 제거했습니다. 오래된 항목을 자동 삭제하지 않으며 큰 요청·응답도 원본 바이트 그대로 보관합니다. 수집 ON/OFF와 Scope만 설정은 기존 동작을 유지합니다.

원본은 확장 실행 동안 전용 임시 파일에 저장하고 목록에는 메타데이터와 디스크 위치만 남깁니다. 선택한 패킷은 필요할 때 복원합니다. 목록 비우기는 대기 항목과 원본 파일도 정리하며, 확장 해제 시 파일을 삭제합니다. 디스크 부족 등 저장 오류는 상태 표시와 Errors에 기록하고 후속 요청 처리를 계속합니다. 0.25.1의 타이머·관찰 단계 오류 격리도 유지합니다.

고정된 건수·패킷 크기 제한을 없앤 것이며, 디스크 용량·목록 메타데이터 메모리 등 시스템 자원은 필요합니다. Burp 프로젝트 파일에 영구 저장되는 기능은 아닙니다. 비정상 프로세스 종료 시 OS 임시 폴더에 파일이 남을 수 있습니다. 재현·분석 도구 자체의 기존 처리 한도 및 한 번에 선택 가져오기 20건 제한은 트래픽 보관과 별개입니다.

## 실제 Burp 확인

Burp Suite Community Edition 2026.3.3과 Java 21의 별도 임시 프로필에서 배포 JAR의 진입점을 실제 로드했습니다. headless 실행이며 GUI 클릭·브라우저 조작 검증은 아닙니다.

- 로컬 서버 → 실제 Burp Proxy → HTTP history / Workbench: 각각 601건.
- 2MiB+17바이트 바이너리 요청·응답: 프록시 수신과 디스크 복원 결과가 원본과 일치.
- 수집 누락 0건, 처리 오류 0건.
- 목록 비우기 및 확장 해제 후 임시 원본 파일 삭제 확인.

[실행 기록](../audit/0.25.2/native-capture-result.txt) · [실제 Burp 검증 코드](../audit/0.25.2/NativeCaptureCheck.java)

이 실행의 Burp headless 시작 로그에는 Burp 자체 ComponentUI 경고가 있었습니다. 위 수집·원본 복원·정리 검사는 완료했지만 화면 품질까지 검증한 것으로 해석하지 않습니다.

## 설치

[다운로드](../downloads/README.md)에서 0.25.2 JAR를 받아 기존 Workbench를 해제한 뒤 Extensions → Add → Java로 등록합니다. 새 확장을 로드한 이후의 응답부터 수집합니다. 과거 HTTP history 전체를 자동 이관하지는 않습니다.
