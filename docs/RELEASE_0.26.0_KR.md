# Workbench 0.26.0 · Feature Mapper 0.2.0

2026-10-15 소스 검토의 P1·P2 우선순위 전체를 적용했습니다. 실습 사이트는 검증된 3.5.2를 유지합니다. 이전 JAR·소스 ZIP·Docker 파일은 덮어쓰지 않습니다.

| 우선순위 | 변경된 동작 |
|---|---|
| 수집·화면·분석 분리 | 원본과 메타데이터를 디스크 색인으로 관리하고 메타데이터 캐시는 256행으로 제한합니다. 목록의 행 벡터 중복 보관을 없애고 새 행을 묶어서 게시합니다. 환경·인증 분석은 한 패킷씩 백그라운드에서 준비해 작은 결과만 화면에 반영합니다. |
| Mapper 인덱스·저장 | 기능→패킷과 브라우저 요청 후보 인덱스를 추가했습니다. 저장 시점 스냅샷을 확보한 뒤 JSON 변환·원본 복사·ZIP 압축을 수집 잠금 밖에서 수행합니다. 저장 중 프로젝트를 바꿔도 스냅샷 원본을 보존합니다. |
| 큰 증거의 메모리 중복 | 전체 요청·응답 문자열 대신 전용 디스크 참조를 보유합니다. 64KiB 단위 원본 복사, 제한된 미리보기, 항목별 ZIP 출력과 파일 해시 스트리밍을 사용합니다. 증거 비우기·종료 시 임시 원본을 정리합니다. |
| JS 캐시 총량 | 원본·미리보기·결과·복원 소스맵을 24MiB 추정 바이트 LRU로 관리합니다. 대기/실행 스냅샷은 16MiB 예산과 기존 100개 큐 제한을 함께 적용합니다. 선택한 소스를 보호하고 퇴출·절단·대기량을 표시합니다. |
| 화면의 전체 재생성 축소 | Activity·Assessment와 Mapper에서 변경된 행만 갱신합니다. 계산한 엔드포인트·업무 결과를 캐시하고 해당 데이터 변경 시 무효화합니다. 숨은 탭의 주기 갱신을 미룹니다. 역할·조직·중요 입력·증거 변경의 재검토 처리는 유지합니다. |
| 구조·버전·검증 일관성 | 저장소·관찰 작업·테이블·JS 캐시/대기열 책임을 별도 클래스로 분리하고 수정한 코드 형식을 통일했습니다. 각 확장의 BuildInfo를 JAR·화면·빌드·검증 버전의 기준으로 사용합니다. 검사 건수는 실제 실행 결과에서 집계합니다. PR과 작업 브랜치 push의 중복 CI 실행도 정리했습니다. |

## 증거 형식 변경

새 증거 ZIP의 `schemaVersion`은 `2`이며, `version`도 호환 필드로 `2`를 기록합니다. `producerVersion`에는 확장 버전을 기록합니다. `packetId`는 전체 요청·응답 해시와 응답 존재 여부로 계산하고, `evidenceId`는 개별 증거 항목을 구분합니다.

`requestRawSha256`·`responseRawSha256`와 원본 크기는 Burp API가 제공한 전체 HTTP 바이트를 나타냅니다. 텍스트 미리보기와 가림 처리 후 출력 텍스트의 해시·크기는 별도로 기록합니다. 바이트를 UTF-8로 읽으며 잘못된 시퀀스는 대체 문자로 표시하므로 텍스트 해시를 원본 해시로 취급하면 안 됩니다. 원본 패킷은 로컬 임시 저장소에 보존하며 ZIP에는 자동 포함하지 않습니다. 기존 증거 가림과 이미지 제한을 유지합니다.

기존 증거 JSON을 처리하는 외부 스크립트는 schemaVersion 2의 해시 출처와 절단 필드를 확인해야 합니다. 0.25.x의 과거 증거 파일과 배포 자료는 수정하지 않습니다.

## 사용 범위와 확인 방법

정식 로컬 release는 Workbench 1,943개 검사(46개 Java 그룹 1,445개·페이로드 HTTP132개·전체 기능 HTTP100개·모의 진단266개), Mapper Java75개·Node7개, Swing108화면·안내48화면을 통과했습니다. [변경 전후 성능 비교](PERFORMANCE_0.26.0_KR.md)에는 동일 어댑터에서 수집3,900건의 정합성, 화면 배출·Mapper 조회 개선과 색인 저장·입력 비용을 함께 기록했습니다.

- ON/OFF/SCOPE, 전체 목록 검색과 원본 바이트 보관을 유지합니다. 메타데이터/JS 캐시 퇴출은 원본 패킷 삭제가 아닙니다.
- JS의 24MiB는 UTF-16 문자열과 레코드 오버헤드의 추정 예산입니다. 편집 문서·실행 중 파서를 포함한 JVM 전체 힙 상한은 아닙니다.
- Mapper 저장의 메타데이터 스냅샷 복사는 여전히 짧은 잠금 안의 O(N) 작업입니다. 전체 저장이 무조건 무중단이라는 의미는 아닙니다.
- 대량 목록의 사용자가 실행하는 전체 검색·정렬은 모든 메타데이터를 검사합니다. 별도 검색 인덱스와 백그라운드 검색은 추가 개선 여지가 있습니다.
- Workbench의 영속 프로젝트 저장·재개와 Workbench–Mapper 전체를 관통하는 공통 ID 연결은 별도 고도화 후보입니다. 이번에는 검토표의 P1·P2 항목과 증거 내부 패킷 ID를 구현했습니다. Mapper의 기존 `.fmkr` 프로젝트 형식 1은 유지합니다.
