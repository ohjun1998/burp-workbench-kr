# Workbench Next 0.52.0 — 설치와 기능별 상세 가이드

**0.52.0은 기존 Workbench KR 0.49.1과 구분되는 Next 버전입니다.** Next 0.50.0의 간결한 메뉴를 유지하면서 설정 재사용, 여러 쓰기 요청의 조회 규칙, 기능 매핑과 점검 업무 연결, 실행·증거 추적, 많은 분석 기록을 다루는 방식을 개선했습니다. 내장 Feature Mapper는 **0.3.4**, 실습 사이트는 **3.10.0**입니다.

이 가이드는 기능 하나를 한 페이지에 제한하지 않고, **원본 선택 → 설정 → 실행 → 근거 확인 → 증거 저장** 순서로 설명합니다. 각 단계표의 **🔴 번호**는 누를 순서, 굵은 글씨는 화면에 표시되는 버튼·탭입니다. 예제의 `https://example.test`와 `/api/notices/101`은 설명용 값이므로 실제로 점검하는 대상에 맞춰 바꾸세요.

## 1. 이번에 달라진 부분

| 구분 | Next 0.50.0에서 제공하던 동작 | Next 0.52.0의 추가·변경 |
|---|---|---|
| 화면 구성 | 주요 메뉴 8개, 공통 선택 원본, F1 기능 안내 | 구조 유지. 설정과 실행·증거 연결을 보강 |
| 권한 설정 보조 | 선택 요청의 권한표 사전 입력, 보관 GET·JSON 필드 선택 | 후보창을 먼저 열고 백그라운드에서 복원·파싱. 취소와 오래된 결과 폐기 |
| 비교 준비 | 요청·계정별 설정 상태와 판정 한계 표시 | 선택 행의 계정·권한표·쓰기 조회로 바로 이동하고 같은 원본으로 재검토 |
| 쓰기 결과 조회 | 하나의 조회 설정을 구성 | 이름 있는 Origin·메서드·경로별 규칙을 최대 32개 관리하고 요청별 적용 |
| 설정 재사용 | 화면에서 설정 | 역할 자리표시자를 쓰는 이름 있는 묶음 등록·적용·JSON 저장/불러오기 |
| 기능 매핑과 업무 | 기능 분류와 점검 진행 현황을 같은 메뉴 아래 배치 | 선택 기능의 API로 업무 초안 생성·갱신, 요구 계정과 추가·제외 범위 검토 |
| 실행과 증거 | 비교 당시 근거를 증거에 포함 | 업무·정확한 원본·실행 ID·계정별 조건 revision·저장 ZIP 연결 |
| JS 기록 | 디스크 이력, 보관 원본 재시도 | 200개 단위 이력 페이지, 보존 표시·수동 정리, 선택한 기록의 필요한 내용 읽기 |
| 처리 부담 | 분석 큐, 캐시, 최신 검색 유지, 시간 진단 | 검색의 새 구간 재사용, JS 정적 문법 전처리 캐시, 응답 복원·디코딩 예약 예산 |

이전 버전의 검증 횟수나 탐지 성능을 0.52.0의 결과로 합산하지 않습니다. 0.50.0 사용법과 당시 제한은 [기존 Next 안내](RELEASE_0.50.0_NEXT_KR.md)에 보존합니다.

## 3. 처음 사용할 때 필요한 말과 화면

| 용어 | 이 가이드에서 뜻하는 것 | 예시 |
|---|---|---|
| 원본 | 목록에서 선택한 한 번의 요청·응답 | 같은 URL이어도 본문·계정·시각이 다르면 다른 원본 |
| Origin | 프로토콜·호스트·포트의 조합 | `https://example.test:443` |
| 권한표 | 계정별로 기대하는 허용·차단 정책 | 관리자 `ALLOW`, 일반 사용자 `DENY` |
| 쓰기 조회 | 쓰기 요청 전후에 GET으로 실제 상태를 관찰하는 설정 | PATCH 전후 `$.title` 확인 |
| 설정 묶음 | 이름·대상·revision이 붙은 재사용 설정 | `공지 수정 권한 · r2` |
| 점검 계정 | 진행 현황에 등록한 계정 기록 | 관리자, 일반 사용자, 비로그인 |
| 업무 | 점검할 API와 요구 계정의 묶음 | 공지 관리: 조회·수정·삭제 |
| 실행 | 비교를 시작해 종료한 한 번의 처리 | 고유 실행 ID, 조건 revision, 종료 상태 |

**설정 적용**, **실행 종료**, **취약점 판단**, **업무 완료**는 각각 다른 상태입니다. 설정을 저장했다고 요청이 실행되지는 않습니다. HTTP 200이나 실행 완료 표시만으로 권한 우회 또는 업무 완료가 확정되지는 않습니다.

| 하려는 일 | 열 화면 |
|---|---|
| 원본 선택·범위·검색 | 요청·응답 목록 |
| 기능과 업무 만들기 | 기능 자동 매핑 → 기능 분류·실행 / 점검 진행 현황 |
| 계정 대조·정책·쓰기 조회 | 계정 권한 비교 |
| JS 기록·API 후보 | JS에서 API 찾기 |
| 응답 단서·분석 제외 사유 | 응답 보안 분석 |
| 증거 검토·ZIP 저장 | 재현·증거 정리 |

상단 **기능 안내** 또는 **F1**은 현재 도구·하위 화면의 안내를 엽니다. 변환·JWT는 **요청·응답 목록 → 변환·비교**, URL 수집은 **서버·경로 탐색 → URL 후보 수집**에 있습니다.

## 4. 재사용할 계정 비교 설정 묶음 만들기

**처음에는 가져올 묶음이 없어도 됩니다.** 먼저 원본을 선택하고 5~6장의 조회·권한 규칙을 만든 다음 이 장의 등록·내보내기로 돌아오세요. 이미 저장한 JSON이 있으면 아래 순서로 불러옵니다.

| 단계 | 화면에서 할 일 | 확인할 내용 |
|---|---|---|
| 🔴 ① 원본 고정 | **요청·응답 목록**에서 대상 원본을 한 개 선택합니다. | 적용할 Origin·메서드·경로가 맞아야 합니다. |
| 🔴 ② 창 열기 | **계정 권한 비교 → 더보기 → 설정 묶음 · 저장/불러오기**를 엽니다. **비교 설정** 안에서도 같은 창을 열 수 있습니다. | 이름·목록·내용 미리보기·등록/적용/JSON 버튼이 보입니다. |
| 🔴 ③ 목록에 등록 | 현재 설정을 재사용하려면 이름을 입력하고 **현재 설정 묶음 등록**을 누릅니다. | 저장 전 전체 설정과 제외되는 항목을 검토합니다. 등록만으로 현재 설정을 다시 적용하지 않습니다. |
| 🔴 ④ 파일 저장 | **JSON 저장·내보내기**를 눌러 내용을 검토하고 파일 위치를 고릅니다. | 목록 등록은 현재 확장 실행 중에 유지됩니다. 재시작 후 사용하려면 JSON으로 저장해야 합니다. |
| 🔴 ⑤ 파일 불러오기 | **JSON 불러오기**에서 이전 파일을 선택하고 검토합니다. | 목록으로 가져올 뿐, 활성 비교 설정을 자동 변경하지 않습니다. |
| 🔴 ⑥ 명시적 적용 | 목록에서 묶음을 선택하고 대상·revision을 읽은 뒤 **선택 묶음 적용**을 누릅니다. | 현재 원본이 묶음의 Origin·메서드·경로에 맞고 SCOPE 안인지 확인합니다. |
| 🔴 ⑦ 계정 재연결 | 인증 후보를 비교 계정에 다시 지정하고 소유값·역할·신원 확인 및 필요한 갱신 설정을 검토합니다. | 적용 시 비교 계정 지정과 신원·갱신 연결이 해제됩니다. 인증 후보 목록은 남습니다. 쓰기 전송 허용도 다시 선택해야 합니다. |

묶음은 `역할 1`, `역할 2`, `역할 3`, `비로그인` 자리표시자를 사용합니다. Cookie·Authorization·토큰, 실제 인증 후보와 세션 연결을 저장하지 않습니다. 권한표, JSON 경로, 업무 기대값 같은 검사 설정은 저장되므로 내보내기 전 내용을 읽으세요. 알려진 인증 키·토큰 형태는 거부하지만 임의 업무 문구가 민감한지까지 자동 판단하지는 않습니다.

새 묶음은 revision 1부터 시작하고 같은 묶음을 갱신하면 revision이 증가합니다. 검토 중 revision이 바뀌거나 불러온 파일이 기존 이름·대상 설정과 충돌하면 조용히 덮어쓰지 않고 거부합니다. 현재 목록과 파일을 비교한 뒤 의도한 이름·설정을 다시 등록하세요. 가져오기 실패는 부분 등록으로 처리하지 않습니다.

## 5. 쓰기 요청마다 다른 조회 규칙 지정하기

예를 들어 `PATCH /api/notices/101`은 공지 제목을, `PATCH /api/profile`은 사용자 설정을 조회해야 합니다. 두 요청을 함께 비교할 때도 각각 다른 GET·JSON 경로가 적용되어야 합니다.

| 단계 | 화면에서 할 일 | 예시·주의점 |
|---|---|---|
| 🔴 ① 대상 연결 | 쓰기 원본 한 개를 선택합니다. **비교 설정**의 쓰기 조회 영역에서 **새 규칙 → 선택 요청 연결**을 누릅니다. | Origin·PATCH·`/api/notices/101`을 확인합니다. 연결만으로 조회나 쓰기를 실행하지 않습니다. |
| 🔴 ② 이름 지정 | 알아보기 쉬운 규칙 이름을 입력합니다. | `공지 제목 수정 확인`처럼 무엇을 확인할지 적습니다. |
| 🔴 ③ GET 후보 | **관측 GET 후보**를 엽니다. 로딩 화면에서 기다리거나 **취소**할 수 있습니다. | 같은 Origin·현재 SCOPE의 보관된 GET 응답만 읽습니다. 서버에 새 GET을 보내지 않습니다. |
| 🔴 ④ URL 적용 | 실제 변경을 확인할 수 있는 행을 선택하고 **선택 URL을 조회 설정에 적용**을 누릅니다. | 경로가 비슷하다는 이유만으로 결과 확인 API라고 확정하지 않습니다. 후보가 없으면 직접 입력합니다. |
| 🔴 ⑤ 필드 선택 | **보관 JSON 필드**를 열어 경로를 선택하고 **선택 경로 적용**을 누릅니다. | `$.title` 같은 경로만 적용합니다. 오른쪽 과거 관측값을 기대값으로 자동 복사하지 않습니다. |
| 🔴 ⑥ 목표 설정 | 기대값·관찰 방식·최대 조회 횟수를 입력하고 **쓰기 요청 전후 조회로 처리 결과 확인**을 선택합니다. | 예: `"점검 안내"`로 변경되는지 확인. 변경·삭제·숫자 경계 등 목적에 맞는 방식을 고릅니다. |
| 🔴 ⑦ 저장 | **규칙 저장·갱신**을 누릅니다. | 저장된 조회 규칙 목록에 이름이 표시됩니다. 설정 저장만으로 HTTP 요청을 보내지 않습니다. |
| 🔴 ⑧ 추가 | 다른 쓰기 원본을 선택하고 **새 규칙**부터 반복합니다. | 두 번째 규칙은 해당 요청의 Origin·메서드·경로와 GET·필드를 별도로 지정합니다. |
| 🔴 ⑨ 점검 | 목록에서 규칙을 선택해 **규칙 불러오기**로 확인하거나 **선택 규칙 삭제**로 정리합니다. | 불러온 규칙의 편집 내용은 다음 비교 설정에 반영됩니다. 저장해 목록과 편집 내용을 맞추세요. |

실행 시 원본의 Origin·메서드·경로에 맞는 활성 규칙을 선택합니다. 같은 요청에 여러 활성 규칙이 걸리는 충돌은 실행 전에 막습니다. 예를 들어 같은 Origin에서 `PATCH /api/items/{id}`와 `PATCH /api/items/101`을 동시에 활성화하면 범위가 겹칩니다. 경로 범위를 나누거나 한쪽 사용을 해제하세요. 서로 다른 Origin의 규칙을 같은 대상이라고 취급하지 않습니다.

후보창을 연 뒤 원본·Scope·조회 설정이 바뀌면 이전 결과를 적용할 수 없습니다. 같은 URL의 다른 원본도 선택 변경입니다. 창을 다시 열어 현재 조건으로 후보를 읽으세요. 보관 원본이 만료된 경우 새 요청으로 대신 채우지 않습니다.

쓰기 조회는 원본 기준 인증으로 전후 GET을 보냅니다. 쓰기 요청은 비교 계정당 한 번만 전송하며 되돌리지 않습니다. 기준 쓰기 요청을 한 번 더 보내는 방식으로 기준 응답을 만들지 않습니다. 조회값 불변, 403, 200 중 하나만 보고 실제 쓰기 성공·차단을 확정하지 않습니다.

| 🔴 ⑧ 같은 원본 재검토 | **같은 원본 준비 다시 확인**을 누릅니다. | 행 수정에서 선택한 정확한 원본으로 준비 화면을 다시 엽니다. 원본 선택이 바뀌었다면 처음부터 준비를 다시 열어야 합니다. |

여러 원본을 준비한 화면에서 특정 행을 수정하면 **그 행의 원본**으로 수정·재검토를 이어갑니다. 전체 선택 묶음을 다시 실행하려면 목록에서 대상들을 다시 선택하고 **선택 요청 비교**를 여세요. 같은 메서드·URL이라도 다른 본문을 가진 원본을 첫 번째 요청으로 바꿔 쓰지 않습니다.

준비 화면의 ‘설정 적용’은 실행에 사용할 규칙을 찾았다는 뜻입니다. 실제로 GET을 보냈는지, 쓰기 결과가 바뀌었는지, 계정이 올바른지는 실행 결과에서 따로 확인합니다. 필요하면 세션 검사에 신원 확인 GET·JSON 경로·기대 신원을 지정하세요. **세션 검사를 실제로 실행하는 동작은 HTTP 요청을 보냅니다.**

| 단계 | 화면에서 할 일 | 실제로 일어나는 일 |

| 🔴 ② 시작 | **비교 시작** 또는 제한을 확인한 뒤 **제한 확인 후 비교**를 누릅니다. | 여기서 실제 HTTP 재전송과 필요한 기준·전후 GET이 시작됩니다. |
| 🔴 ③ 상태 확인 | 계정 비교 이력에서 실행 상태를 확인합니다. 필요하면 **중지**를 누릅니다. | 진행 중·완료·중단과 응답 판정을 구분합니다. 중지는 남은 전송을 막으며 이미 전송한 쓰기를 되돌리지 않습니다. |

정상 종료한 실행도 정책이 미정이거나 근거가 부족하면 판정은 ‘확인 필요’일 수 있습니다. 실패·중지·진행 중인 최근 실행은 현재 조건의 완료 근거로 인정하지 않습니다. 관련 계정·API의 권한 또는 조회 규칙을 바꾸고 설정을 확인하면 해당 API와 의존 업무가 재검토 대상으로 바뀝니다. 무관한 다른 API의 정책 변경을 모두 같은 변경으로 취급하지 않습니다. 설정 묶음 적용은 해당 Origin의 계정 재연결을 요구합니다.

**요청 비교 ON**은 단순 기록 버튼이 아닙니다. 이후 조건에 맞는 Proxy·Repeater 신규 요청을 계정별로 자동 재전송합니다. 처음 사용하는 경우 수동 **선택 요청 비교**로 흐름을 확인한 뒤 필요할 때 켜세요. 준비 화면의 자동 비교 안내를 읽고 시작하며 종료할 때 OFF로 바꿉니다.

## 9. 실행 결과를 증거 ZIP과 업무 완료에 연결하기

| 단계 | 화면에서 할 일 | 확인할 내용 |
|---|---|---|
| 🔴 ① 실행 선택 | 계정 비교 이력에서 종료한 실행 결과 한 개를 선택합니다. | 아직 실행 중인 결과를 완성된 증거로 추가하지 않습니다. |
| 🔴 ② 증거 추가 | **재현·증거 정리 → 권한 비교 추가**를 누릅니다. | 원본, 읽기 기준, 계정별 전송, 쓰기 전후 조회와 당시 설정·판정 이유가 묶입니다. |
| 🔴 ③ 설명 작성 | 영향·재현 순서·관찰한 결과·남은 확인 사항을 적습니다. | 자동 추정과 직접 확인한 사실을 구분합니다. |
| 🔴 ④ 가림 확인 | **가림 미리보기**에서 헤더·쿼리·선택한 본문·직접 작성한 설명을 확인합니다. | 이름을 알 수 없는 개인정보와 첨부 이미지는 직접 검토합니다. |
| 🔴 ⑤ 파일 저장 | **증거 ZIP 저장**을 누릅니다. | 실제 파일 저장 성공 이후에 ZIP SHA-256과 실행 연결을 기록합니다. 미리보기만으로 저장 완료가 되지 않습니다. |
| 🔴 ⑥ 연결 재확인 | **실행·증거 연결**에서 저장 ZIP을 확인합니다. | ZIP의 `coverage.json`에는 증거 항목 ID와 실행 ID 및 원본·정책 메타데이터의 연결이 남습니다. |
| 🔴 ⑦ 수동 완료 | **점검 진행 현황**에서 필요한 **URL 완료**, 이후 **업무 완료**를 검토합니다. | 요구 계정×API, 중요 입력, 증거 조건이 충족됐는지 확인하고 사람이 완료합니다. |

ZIP은 가린 텍스트·메타데이터·원본 해시를 제공하며 전체 원본 바이트나 로그인 자격정보를 복구하는 파일이 아닙니다. 재현에는 로컬 원본과 사용자가 확인한 계정 조건이 필요합니다. 비교 묶음을 추가했을 때 전체 증거 32개 한도를 넘으면 추가 전에 거부합니다.

진행 현황의 저장·불러오기는 실행·증거 **메타데이터**를 보존합니다. 인증값·원본 패킷은 저장하지 않으며, 불러온 과거 실행은 현재 계정과 조건을 다시 확인하기 전 완료 근거로 인정하지 않습니다. 저장 당시 진행 중이었던 실행은 복원 시 중지 상태로 다룹니다. 과거 증거와 이력 자체를 지우는 것은 아닙니다.

| 🔴 ⑤ 기준 설정 | **보존·디스크 설정**에서 보존 기간 기준, 일수, 디스크 알림 기준을 확인하고 **기준 저장**을 누릅니다. | 기준 저장이나 알림 기준 초과만으로 파일을 자동 삭제하지 않습니다. |

보존 일수는 1~3,650일, 화면의 디스크 알림 기준은 1~65,536MiB입니다. 알림 기준은 디스크 강제 상한이나 자동 삭제 조건이 아닙니다. 디스크를 읽을 수 없거나 기록이 손상된 경우 표시 오류를 확인하고 필요한 원본을 보관하세요.

같은 JS 내용은 문법 호환 전처리의 공통 부분을 재사용합니다. 요청·계정·Origin·페이지 문맥과 최종 API 판단을 섞어서 공유하는 캐시가 아닙니다. 별도 캐시는 추정 4MiB·최대 128항목이며 1Mi 문자를 넘는 입력 단위는 이 캐시에 보관하지 않습니다. 실제 JVM 전체 메모리 제한으로 해석하지 않습니다.

## 11. 검색과 응답 분석이 느리거나 일부 빠질 때

### 요청·응답 검색

1. **요청·응답 목록**에서 검색어와 메서드·응답·계정·기간·검색 범위를 정합니다.
2. 새 원본이 추가될 때 같은 조건의 기존 검색 결과를 활용하고 필요한 새 구간을 검사합니다. 삭제·조건 변경·기간 만료는 다시 반영합니다.
3. 다른 검색어를 입력하면 이전 작업을 취소하고 최신 작업을 기다립니다. **검색 취소**를 누르면 새 트래픽만으로 취소한 검색을 다시 시작하지 않습니다.
4. 잘못된 정규식 또는 512자를 넘는 검색어라면 이전 결과를 보존합니다. 검색 조건을 고쳐 다시 실행하세요.
5. 본문 검색은 읽기 한도가 있으므로 부분 검색 표시를 확인합니다. 검색 결과가 없다고 한도 밖 본문에도 해당 값이 없다고 단정하지 않습니다.

### 응답 보안 분석과 보관 원본 재시도

| 단계 | 화면에서 할 일 | 해석 |
|---|---|---|
| 🔴 ① 상태 보기 | **응답 보안 분석 → 분석 처리·재시도**를 엽니다. JS는 **더보기 → 분석 처리·재시도**를 사용합니다. | 대기·분석 중·완료·일부 분석·큐 제외·실패·중지·원본 만료를 구분합니다. |
| 🔴 ② 원인 읽기 | 해당 행의 제한 사유와 화면 아래 상태줄 설명을 확인합니다. | 큐 부족, 본문 크기, 원본 복원 크기, 디코딩 예산, 형식 문제는 서로 다릅니다. |
| 🔴 ③ 재시도 | 대기가 줄었으면 재시도 가능한 행에서 **선택 원본 다시 분석**을 누릅니다. | 같은 URL의 최신 응답 대신 그 행의 정확한 보관 원본을 로컬에서 읽습니다. 서버 요청은 없습니다. |
| 🔴 ④ 범위 확인 | 새 상태와 실제 발견 결과를 함께 읽습니다. | 크기·형식·Scope 한도는 재시도로 우회되지 않습니다. |

응답 분석은 대기 입력 보유에 **16MiB**, 복원·디코딩 작업에 **224MiB**의 추정 예약 예산을 둡니다. 수신 본문은 **2MiB**, 요청+응답 원본 복원은 **5MiB** 한도를 적용합니다. 일반 문자열 규칙은 앞 **1Mi 문자**, JSON 순차 구조 분석은 **2Mi 문자** 범위를 안내합니다. 이 예산은 바이트·문자 복사 비용을 계산한 내부 예약이며, 파서·증거 캐시·Burp·다른 확장을 포함한 JVM 전체 heap 상한이 아닙니다.

상태줄에 마우스를 올리면 입력 보유 예약, 복원·디코딩 예약, 예약 제외 수를 볼 수 있습니다. 처리가 끝나거나 취소되면 예약을 돌려줍니다. 최근 재시도 메타데이터는 256건이며, 목록에서 빠졌다는 이유로 원본 트래픽이나 기존 분석 결과가 자동 삭제되지는 않습니다. 원본이 이미 만료됐다면 같은 URL로 재요청해 대체하지 않습니다.
