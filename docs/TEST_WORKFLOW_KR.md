# 커뮤니티 모의 진단 흐름

[다운로드](../downloads/README.md) · [PDF 가이드](../downloads/guides/README.md) · [0.24.0 변경 안내](RELEASE_0.24.0_KR.md)

LOOP 커뮤니티의 취약·수정 구현을 같은 조건으로 비교하는 절차입니다. HTTP 응답 관찰, 계정별 정책, 실제 상태 변화, 브라우저 실행 근거를 구분해 기록합니다. 이 문서는 재현 절차이며 이 절차 전체를 현재 환경에서 실제 Burp로 실행했다는 검증 보고서는 아닙니다. 실행한 범위는 [버전별 검증 기록](VERIFICATION_0.24.0.json)을 확인합니다.

0.24.0에서는 버튼 위치와 이름을 정리했습니다. [화면·버튼 안내](UI_0.24.0_KR.md)도 함께 확인하세요. 실습 사이트는 3.5.0을 그대로 사용합니다.

| 하려는 동작 | 0.24.0 위치 |
|---|---|
| 전체 URL의 완료·입력 완료·발견 근거·Repeater 초안 | 활동 추적 → URL 점검 현황 |
| 계정별 API·입력 완료 | 활동 추적 → 계정별 점검에서 계정과 API·입력 선택 |
| 업무에서 API 연결·제외 | 업무별 현황 하단의 요구 계정 × API 상세 표 |
| 증거 파일 상태·재연결·재검증 | 업무별 현황 → 증거 파일 ▾ |
| API 문서의 요청 초안 | 응답 분석 → API 문서 → Repeater 초안 |
| 저장/조회 마커와 실행 근거 | 응답 분석 → 저장/조회 연결 |

선택한 항목이나 준비된 결과가 필요한 버튼은 조건을 갖췄을 때 활성화됩니다. 회색 버튼이 보이면 먼저 해당 표의 계정·API·입력·결과 선택을 확인합니다.

## 1. 기준과 계정을 먼저 준비하기

Docker 실행 패키지를 시작하고 Burp 브라우저로 `http://127.0.0.1:8088`을 엽니다. 확장의 트래픽에서 실습 요청을 선택해 우클릭 → **SCOPE 지정**으로 대상 경로 또는 도메인을 추가합니다. 계정을 바꿔도 같은 실습 Origin을 사용합니다.

실습 계정 `alice`, `bob`, `moderator`, `admin`의 암호는 모두 `LabOnly!2026`입니다. 권한 비교의 세션과 활동 추적의 점검 계정을 명시적으로 연결합니다. Alice/Bob/Admin/비로그인을 한 번에 혼동하지 말고, 우선 소유자 Bob과 타인 Alice의 정상 요청부터 확인합니다. 역할·조직은 사용자가 선언한 조건이며 실제 로그인 주체를 자동으로 증명하지 않습니다.

업무별 현황에 점검 목적, 요구 계정, 요구 API를 등록합니다. 중요한 업무는 **모든 입력 수동 완료 필수**, **모든 계정×API의 파일 확인 증거 필수**를 선택합니다. 객체 선택에 영향을 주는 입력만 `URL:id`, `BODY:ownerId`처럼 중요 입력으로 지정하고 정상 요청을 관측해 기준을 잡습니다.

## 2. 수집한 요청을 정책별로 비교하기

| 점검 | 실습 대상 | 확인할 근거 |
|---|---|---|
| 비공개 글의 교차 계정 접근 | `/api/community/{mode}/posts/102` | Bob 정상 조회, Alice 취약 경로 접근, 수정 경로 404, 소유자 재조회 |
| 비공개 첨부·쪽지 | `/api/community/{mode}/files/bob-private-file`, `/api/community/{mode}/messages/202` | 상태 코드뿐 아니라 실제 비공개 내용과 접근 주체 |
| 검색 입력 처리 | 커뮤니티 검색 요청 | 정상 기준·검사 요청·대조 요청의 본문 차이 |
| 저장형 출력 | 댓글 등록 후 조회 | 저장한 고유 마커, 조회 계정, HTML/문자 출력 구분 |
| 업로드 후속 동작 | 첨부 업로드 후 조회·다운로드 | 수락 여부, 저장된 내용, MIME, 접근 권한 |
| JS·문서 기반 발견 | `/js-lab`, `/diagnostics`, `/v3/api-docs` | 원본 소스 위치, 메서드, 미확정 경로와 실제 관측 구분 |

`{mode}`는 `vuln` 또는 `fixed`입니다. 공개 객체, 소유자 전용 객체, 공유 객체를 서로 다른 정책으로 설정합니다. URL 형태와 상태가 같아도 권한 정책이 다를 수 있습니다. 소유자 전용 객체에는 소유자·타인·관리자별 ALLOW/DENY 기대값을 정하고 권한 비교 결과를 읽습니다.

404/410만으로 차단이나 삭제를 확정하지 않습니다. 같은 대상·인증 조건의 소유자 재조회와 응답 본문이 존재 근거를 뒷받침하는지 확인합니다. 요청 대상·세션이 바뀌거나 본문이 불안정하면 재검토합니다. 쓰기 요청은 실습용 임시 객체를 만들고 요청 후 소유자 조회로 실제 변경 여부를 확인합니다.

### 사이트 3.5의 추가 시나리오

`http://127.0.0.1:8088/bounty-lab`에서 아래 시나리오를 실행합니다. `/api/bounty/manifest`에 정책·경로·보관 한도가 있습니다. 자세한 설명은 [사이트 3.5 실습 안내](../project/burp-development-workspace/community-security-lab/BOUNTY_LAB_3.5_KR.md)를 확인합니다.

| 시나리오 | 경로와 절차 | 수정 구현의 기대 동작 |
|---|---|---|
| 같은 경로 형태의 서로 다른 정책 | `GET /api/bounty/{mode}/objects/{id}`에서 201 공개, 202 Bob 소유, 203 조직 A, 204 Alice·Bob 공유, 205 조직 B, 206 Alice 소유 비교 | 정책상 허용은 200, 차단은 404. admin은 모두 허용 |
| 저장 후 조회 | `POST /api/bounty/{mode}/stored`에 고유 마커가 든 `value` 전송 후 응답 JSON의 `url` 조회 | 소유자만 조회하며 HTML을 문자로 출력 |
| 업로드 후 다운로드 | `POST /api/bounty/{mode}/uploads?name=probe.html`에 원시 파일 본문 전송 후 `url` 조회 | `.txt`만 수락, 소유자만 다운로드, `text/plain`·`attachment` 응답 |

먼저 Bob으로 객체 202를 조회하고 Alice로 같은 객체를 비교한 뒤 Bob으로 다시 조회합니다. 조직 A/B 객체 203·205도 추가해 같은 URL 패턴 안의 정책 차이가 빠지지 않았는지 확인합니다. 조직 A는 Alice·moderator, 조직 B는 Bob입니다. 취약 객체 경로는 로그인 회원의 교차 접근을 허용하므로 수정 경로를 대조군으로 사용합니다.

저장형 출력은 `<b>PR_0123456789abcdef</b>`처럼 무해한 마커로 HTML 출력과 문자 출력을 비교할 수 있습니다. 이 마커가 HTML로 출력돼도 스크립트 실행 근거가 되지는 않습니다. 업로드에서 HTML 응답을 비교하려면 취약 요청에 `Content-Type: text/html`을 지정하고, 수정 대조 요청은 `.txt` 파일로 비교합니다. 수정 구현의 쓰기에는 로그인 응답에서 얻은 `X-CSRF-Token`이 필요합니다. `POST /api/bounty/reset`은 CSRF를 확인하고 현재 계정이 만든 새 실습 데이터만 초기화합니다.

## 3. 후보에서 재현 가능한 증거로 진행하기

페이로드 검사에서는 정상 요청의 입력값 한 곳을 지정하고 필요한 프로필만 실행합니다. 기준·검사·대조 결과를 함께 읽고 Repeater에서 다시 확인합니다. 요청 수·간격은 설정에서 확인합니다. 저장·업로드 검사로 생긴 실습 데이터를 확인하고 정리합니다.

| 관찰 | 그 단계에서 말할 수 있는 것 | 다음 확인 |
|---|---|---|
| 업로드 응답 2xx | 요청 수락 | 후속 조회, 실제 저장, MIME, 타인 접근 |
| 마커가 응답에 다시 나타남 | 저장·조회 또는 반사 관찰 | 출력 위치, HTML 인코딩, 실행 주체 |
| HTML/스크립트 문자열 존재 | 실행 가능성 검토 필요 | Burp 브라우저에서 실제 실행·출처 확인 |
| 오류 문자열·길이·시간 차이 | 이상 응답 후보 | 정상·대조 재실행과 입력 반사 영향 제거 |
| SHA-256이 같은 증거 ZIP | 파일 무결성 확인 | 증거 내용·정책·결론의 타당성 검토 |

업무 흐름 기능은 요청을 단계로 묶어 순차 재현할 때 사용합니다. 0.24.0에서는 왼쪽에 요청·JSON 추출 입력, 오른쪽에 결과 표와 선택 결과의 요청·응답을 배치합니다. 토큰 추출 실패나 기대 결과 불일치가 있으면 후속 단계를 계속 보내기 전에 원인을 확인합니다. 저장형 출력과 업로드는 등록·조회·실행 단계를 나누어 기록하고, 브라우저 증거가 없는 상태를 실행 확인으로 표시하지 않습니다.

**응답 분석 → 저장/조회 연결 → 마커 등록**에서 `WB_` 또는 `PR_`로 시작하는 고유 마커를 등록합니다. 마커를 포함한 쓰기·업로드 요청과 후속 조회를 관측한 뒤 **쓰기 응답 / 조회 재출력 / HTML 출력 / 브라우저 실행** 네 단계를 확인합니다. **선택 흐름 → 증거**는 실제 쓰기·조회 원본 두 건을 연결합니다. 취약·수정 구현과 서로 다른 저장·업로드 시나리오는 각각 고유 마커를 사용합니다. 같은 Origin·마커의 새 쓰기는 이전 조회와 수동 실행 근거를 초기화합니다.

실제 브라우저에서 같은 마커의 실행을 직접 확인했을 때 HTML 조회가 관측된 흐름을 선택하고 **브라우저 실행 확인**으로 가린 PNG/JPEG를 첨부합니다. 이미지 해시와 확인 시각을 기록하며 이미지 내용 자체를 자동 판독해 실행을 증명하지는 않습니다. **실행 근거 해제**로 확인을 취소할 수 있습니다. 새 쓰기 또는 같은 URL의 새 조회는 이전 수동 실행 근거를 무효화하므로 바뀐 흐름을 다시 확인합니다. 원본 캐시가 만료되거나 크기 한도를 넘으면 요청을 다시 관측해야 합니다.

응답 차이를 증거로 남기려면 트래픽에서 요청 하나를 선택하고 **데이터 도구 → 비교**의 **왼쪽 데이터 → 트래픽 가져오기**를 누릅니다. 다른 요청을 선택해 **오른쪽 데이터 → 트래픽 가져오기**로 가져온 뒤 **비교 실행**, **원본 → 증거**를 누릅니다. 양쪽 원본이 연결되어야 증거 버튼이 활성화됩니다. 입력을 직접 편집하면 해당 쪽 원본 연결이 해제되므로 실제 패킷을 다시 가져와야 합니다. 입력 편집으로 돌아가거나 새 원본을 가져오면 이전 결과 탐색은 비활성화되며 다시 비교합니다.

**URL 수집**에서는 명시적으로 GET 검증한 결과를 선택하고 **선택 검증 원본 → 증거**를 사용합니다. 아직 전송하지 않은 발견 URL은 원본 패킷 증거로 취급하지 않습니다. 검증 요청에 인증값을 지정하지 않아도 Burp 세션 규칙이 인증을 넣을 수 있으므로, **GET 상태 · 인증 확인**과 실제 전송 원본을 함께 읽습니다. 연결 원본은 요청·응답 합계 128 KiB 이하 범위에서 보관하며, 비교 화면은 64 KiB·1,500줄 표시 한도가 있습니다. 제한 안내를 읽고 표시된 부분을 전체 응답으로 해석하지 않습니다.

## 4. 증거를 저장하고 업무를 마감하기

**점검 지원 → 증거 묶음**에 선택 트래픽, 권한 비교, 업무 흐름 또는 페이로드 결과를 연결합니다. 실제 영향과 재현 절차에는 계정 역할, 대상 객체, 기대 정책, 정상·검사·대조 결과를 적습니다. 브라우저 실행을 확인했다면 민감 정보가 가려진 화면과 실행 조건을 첨부합니다. 원본 인증·개인정보가 공유 자료에 남지 않는지 저장 내용을 확인합니다.

응답 분석의 Passive 관찰 결과는 **선택 관찰 → 증거**로 실제 대표 원본을 전달합니다. 데이터 비교·URL 수집·저장/조회 연결에서 전달한 원본도 점검 지원의 같은 증거 목록에 모입니다. 원본 요청이 있어야 **가림 미리보기**와 **증거 ZIP 저장**이 활성화됩니다. 저장을 끝내야 파일이 만들어지며, 화면에 전달한 상태만으로 저장 완료가 되지는 않습니다.

계정×API와 입력을 사람이 검토한 뒤 수동 완료하고 업무를 마감합니다. 검사 실행만으로 완료되지 않습니다. 역할·조직·중요 입력이 바뀌거나 증거가 달라지면 재검토 상태를 확인합니다. 계정별 URL을 다시 완료한 뒤에도 업무는 전체 조건을 확인해 다시 마감합니다.

파일을 이동했다면 **업무별 현황 → 증거 파일 ▾ → 증거 ZIP 재연결**로 같은 파일을 연결하고 **모든 증거 재검증**으로 존재·해시를 확인합니다. **파일 상태 확인**에서 마지막 결과를 볼 수 있습니다. JSON을 다시 불러오면 인증 연결과 로컬 파일 확인을 다시 수행합니다. 파일 확인 상태는 마지막 검사 결과이며 실시간 감시가 아닙니다.

## 반복 점검의 효율을 높이기

1. 정상 탐색으로 트래픽을 확보하고 JS·OpenAPI에서 발견한 API를 활동 추적 목록과 대조합니다.
2. 같은 URL 모양에서도 공개·비공개·공유 정책의 사례를 각각 남깁니다. 응답 코드만 같은 샘플로 대체하지 않습니다.
3. 모든 요청에 모든 프로필을 실행하기보다 실제 입력 형식과 기능에 맞는 검사를 선택합니다.
4. 후보를 좁힌 뒤 기준·검사·대조와 실제 영향이 담긴 증거를 묶고, 수동 재현이 되는지 확인합니다.
