처음 사용하는 순서

  1. 설치: 이전 Simple/Strix 확장을 언로드하고1.1.0 JAR를 로드합니다. 기존 설정·진단 기록은 같은 저장 공간을 사용합니다.
  2. 원본 준비: 현재 프로젝트에서 원본을 선택하고 우클릭 선택 원본으로 Strix 진단 준비를 누릅니다.
  3. 조건 확인: 대상·SCOPE·제공자·모델을 확인하고 대화 연결을 선택합니다. 네 번째 원본·테스트 정책 탭에서 기대 정책을 작성하고 진단 입력 미리보기를 확인합니다.
  4. 실행: 실행계획에서 대상과 영향을 확인하고 승인합니다. 대화 연결 상태가 준비될 때까지 기다립니다.
  5. 질문: 내용을 입력하고 전송 확인창에서 대상·질문을 읽은 뒤 승인합니다. 취소하면 보내지 않습니다.
  6. 답변 확인: 전송 수락과 답변 도착을 구분해 읽습니다. 같은 세션에서 후속 질문을 이어가거나 중지합니다.
“방금 계정 간 주문 조회 차이는 어떤 원본에서 확인했나요? 관찰과 추정을 구분하고, 추가 확인이 필요한 점을 설명해 주세요.”

원본 패킷 본문·쿠키·토큰은 자동 전달하지 않습니다. 질문에도 인증값·비밀번호를 붙여넣지 마세요.

전송 전 확인이 필요한 이유

Strix 에이전트는 질문에 답하는 과정에서 도구와 대상 요청을 수행할 수 있습니다. 전송은 읽기 전용 분석을 보장하는 기능이 아니므로 매번 기본 취소인 확인을 거칩니다. 현재 원본·프로젝트·SCOPE·진단 세션이 바뀌면 이전 실행으로 질문하지 않습니다.

최대 에이전트 턴은 HTTP 요청 예산이 아닙니다. SCOPE 확인과 지시문은 Strix 전체 네트워크를 격리하거나 가용성 무영향을 보장하지 않습니다.

별도 Strix 창의 중앙은 진단 대화 / 진행 로그 / 이번 실행 보고서 / 원본·테스트 정책 중 선택한 탭이 넓게 사용합니다. 기존 정책 입력·미리보기는 네 번째 탭에 있으며 메인 메뉴·도구 배치는 유지합니다.

실제 패널 화면

아래는 배포 JAR의 production Swing 화면을 합성 API/세션으로 실행해 캡처한 이미지입니다. 실제 사용자 Burp·모델 추론·대상 진단 성공을 나타내지 않습니다. PNG 픽셀은 수정하지 않았습니다.

연결 상태 읽기

  • 연결 대기: 현재 실행의 live viewer가 준비되는 중입니다. 답변을 받은 상태가 아닙니다.
  • 연결됨: 이번 실행의 인증된 로컬 viewer에 연결했습니다. 전송 수락과 모델 답변은 별도입니다.
  • 종료·실패: 현재 세션으로 새 질문을 보낼 수 없습니다. 자동 새 진단·재전송·다른 제공자 전환은 하지 않습니다.

화면은 모든 에이전트를 합한 최근 대화 최대200개·128Ki자 안에서 선택한 에이전트의 내용을 보여줍니다. 표시 범위 밖의 원본 이력은 Strix 실행 폴더에 유지됩니다.

대화는 Strix에 확정해 저장된 기록을 주기적으로 갱신합니다. 토큰 단위 스트리밍이나 즉시 답변을 보장하지 않습니다. 초기 진단 작업이 완료돼도 소유한 Strix 프로세스가 살아 있고 실행 상한 안이면 후속 질문을 이어갈 수 있습니다.

질문으로 에이전트가 재개되면 초기 턴 예산이 늘어날 수 있습니다. 최대 에이전트 턴은 전체 대화의 엄격한 턴 상한이 아닙니다. 처음 시작한 실행 시간 상한은 질문으로 초기화되지 않습니다. 중지·프로세스 종료·시간 초과 때 연결을 끝냅니다.

필요한 환경과 오류 해결

Linux/macOS의 Python3, 대화 가능한 Strix CLI와 기존 ~/.strix/bin/strix 래퍼가 필요합니다. Windows의 POSIX PTY 대화 연결은 지원하지 않습니다. 기존 비대화형 진단 흐름은 유지하지만 Windows 실행은 이번 검증에 포함하지 않았습니다. 지원 환경에서 대화 연결을 사용할 수 없을 때는 기존 비대화형 진단의 실행·로그·보고서를 사용할 수 있습니다.

Halogen/Qwen 또는 Strix 자체 ChatGPT 구독 인증을 사용합니다. Codex CLI 로그인과는 별개입니다. 전역 모델 설정·OAuth 파일을 변경하거나 인증 토큰을 복사하지 않습니다. viewer 주소·토큰은 로그나 가이드에 표시하지 않습니다.

중지는 이번 실행이 소유한 프로세스에 적용됩니다. 이미 대상 서버에서 시작한 작업을 되돌리거나 별도 Docker 작업의 완전한 종료를 보장하지 않습니다.
