1

트래픽 탭 클릭

Burp 상단의 Workbench KR을 먼저 연 뒤 내부 트래픽 탭을 선택합니다. 여기서 요청을 선택해 각 도구로 전달합니다.

2

트래픽 수집 켜기

체크된 상태에서 Burp를 통과하는 요청과 응답이 목록에 쌓입니다. 브라우저가 Burp 프록시를 사용하고 있는지 확인합니다.

3

요청 행 선택

4

SCOPE 목록 열기

등록한 범위를 별도 창에서 확인합니다. 현재 보고 있는 트래픽 화면과 선택 상태는 유지됩니다.

Scope만은 표시 대상을 줄이는 필터입니다. 점검 범위 자체는 다음 페이지의 우클릭 메뉴로 등록하세요. 데이터 정렬은 표시용이며 전송 원문을 바꾸지 않습니다.

2

URL 경로만 등록

선택 URL의 경로와 그 하위 경로를 포함합니다. 예: /api/community/fixed/posts/101은 해당 경로를 기준으로 등록됩니다. 쿼리 값은 규칙에 저장하지 않습니다.

3

같은 Origin 전체 등록

같은 프로토콜·호스트·포트의 모든 경로를 포함합니다. 실습 사이트 전체를 점검할 때는 http://127.0.0.1:8088/ 범위가 편리합니다.

4

등록 내용 확인

이 메뉴 또는 트래픽 상단 SCOPE 목록 버튼으로 범위를 확인합니다. 각 기능에 URL을 반복 입력하기 전에 여기서 대상 범위를 관리합니다.

Workbench SCOPE는 이 확장의 도구들이 공유하는 범위입니다. Burp의 Target Scope 자체는 변경되지 않습니다. 도메인 전체 규칙은 URL 경로 규칙보다 넓습니다.

04 트래픽을 기능별로 전달하기

트래픽 > 요청 행 우클릭

0.18.0 실습용 예시 화면 · 실제 확장 UI를 창 없이 렌더링 · 클릭하여 확대

1

계정별 인가 비교

먼저 권한 비교 탭에서 계정 후보와 정책을 설정한 뒤 사용합니다. 선택 요청을 다른 계정으로 재전송해 비교하므로 실제 HTTP 요청이 발생합니다.

2

선택 요청으로 검사 준비

요청을 검사 편집기에 가져옵니다. 값 하나를 교체 위치로 지정하고 설정을 확인한 뒤 시작을 눌러야 검사가 실행됩니다.

3

선택 응답의 JS 분석

JS 응답을 가져와 URL/API, 키 후보, 의존성 등을 정적으로 분석합니다. 선택 원본은 JS 추출 탭에서 다시 확인할 수 있습니다.

4

수동 재현 준비

선택 요청을 Burp Repeater로 보냅니다. Repeater에서 값·인증·본문을 확인하고 Send를 눌러 직접 요청합니다.

다른 항목: URL 수집은 대상 URL 수집 화면으로 전달, JWT는 토큰 분석, 변환은 데이터 변환으로 연결합니다. 메뉴 선택과 실제 전송 여부는 기능마다 다릅니다.

1

권한 비교 탭 열기

SCOPE 내 사이트에서 Alice와 Bob으로 각각 로그인해 요청을 발생시킵니다. Cookie와 인증 관련 헤더가 있는 요청이 후보 목록에 기록됩니다.

2

후보 행 선택 후 우클릭

인증 후보는 Origin과 함께 관리됩니다. 원하는 계정의 후보를 클릭하고 우클릭해 계정 슬롯에 지정합니다. 실제 Cookie는 보고서 공유 전에 가리세요.

3

계정 이름과 정책 설정

계정 이름, 소유자 ID, 소유 JSON 경로, 접근 정책을 설정합니다. 다음 페이지부터 지정 순서와 예시를 설명합니다.

4

Record OFF 상태에서 준비

계정·정책 설정이 끝날 때까지 OFF로 둡니다. ON으로 바꾸면 이후 범위 내 요청을 계정별로 자동 재전송합니다.

예시 Cookie는 TRAINING_ONLY 값입니다. 자동으로 수집되는 인증 후보 목록과 명시적으로 실행하는 계정별 재전송을 구분하세요.

07 인가 정책과 비교 기준 설정

권한 비교 > 비교 설정

0.18.0 실습용 예시 화면 · 실제 확장 UI를 창 없이 렌더링 · 클릭하여 확대

1

계정 이름과 소유자 값 입력

Alice=1, Bob=2처럼 응답의 ownerId와 비교할 실제 소유자 값을 넣습니다. 비로그인의 소유자 값은 비웁니다.

2

소유 JSON 경로 지정

예: $.ownerId. JSON 비교 제외에는 $.requestId, $.timestamp처럼 요청마다 달라지는 필드만 넣습니다. 원본 응답은 그대로 보관됩니다.

3

경로별 정책 입력

공개 글은 PUBLIC, 본인만 조회하는 경로는 OWNER_ONLY로 지정합니다. 형식은 GET /api/community/fixed/posts/{id} OWNER_ONLY입니다. 정확한 경로 규칙이 우선합니다.

4

논리적 차단 응답 지정

HTTP 200이어도 error=FORBIDDEN 같은 JSON 값이 차단을 뜻할 수 있습니다. 행별 OR 규칙으로 등록하고 설정 확인을 누릅니다.

쓰기 요청 재전송 허용을 켜면 POST 등 상태를 바꾸는 요청도 비교할 수 있습니다. 해당 실습 동작이 필요할 때만 켜세요. 기본 정책 미설정은 공개/소유자 정책을 모른다는 뜻입니다.

SQL Injection 등 16개 유형 중 대상에 맞는 유형을 고릅니다. 쿼리 값은 URL, JSON 값은 JSON 등 삽입 위치에 맞는 인코딩을 확인합니다.

3

원래 정상 값 설정

예: 검색어 Burp. 이 값으로 정상 응답을 얻고 대조합니다. 적응형/순차 모드와 요청 간격도 함께 확인합니다.

4

총 요청 수와 대기시간 제한

예시는 간격 250ms, 총 한도 100, 대기 10초입니다. 기준·대조 요청도 한도에 포함됩니다. 401/403/429/503 또는 시간 초과 시 중단 사유를 확인합니다.

유형: XSS, SQLI, UPLOAD_NAME, UPLOAD_BODY, DOWNLOAD, SSTI, TRAVERSAL, REDIRECT, CRLF, XXE, XPATH, LDAP, NOSQL, SSRF, COMMAND, CUSTOM. 업로드 재조회와 SSRF 콜백은 해당 실습의 명시적 검증 옵션입니다.

커뮤니티 테스트 사이트로 한 번 따라 하기

사이트가 실행된 상태에서 http://127.0.0.1:8088/diagnostics로 접속하세요.

1 범위 등록

브라우저로 사이트를 열고 트래픽 행 우클릭 > SCOPE 지정 > 선택 도메인 전체 추가. SCOPE 목록에서 127.0.0.1:8088을 확인합니다.

2 계정 비교

Alice·Bob으로 각각 로그인해 후보를 모읍니다. Alice=1, Bob=2, 비로그인을 지정하고 ownerId와 PUBLIC/OWNER_ONLY 정책을 설정합니다. 공개 101과 비공개 102를 비교합니다.

3 JS와 누락 점검

사이트 JS를 관측하고 JS 추출의 URL · API 결과를 확인합니다. 활동 추적에서 발견만 함을 골라 아직 요청하지 않은 URL을 Repeater 초안으로 준비합니다.

4 환경과 URL 확인

환경 탐색에서 없는 경로 비교를 켜고 선택 후보만 검증합니다. URL 수집은 Burp History / JS 출처로 시작해 패턴 대표를 먼저 확인합니다.

5 페이로드 검사

실습용 /api/community/vuln/search?q=Burp 요청을 가져옵니다. Burp를 §PAYLOAD§로 바꾸고 SQLI·URL 인코딩·기준값 Burp를 설정한 후 적은 후보로 시작합니다. 대응하는 fixed 경로도 같은 조건에서 비교합니다.

6 응답 관찰과 마무리

/api/diagnostics/openapi 등 진단 페이지 응답을 관측해 Passive와 API 문서를 확인합니다. WB_ 마커를 등록한 뒤 저장/조회를 실습합니다. 점검한 URL·파라미터를 활동 추적에서 각각 완료하고 기록을 저장합니다.

자주 헷갈리는 동작

SCOPE 목록과 설정을 눌렀는데 작업 탭이 그대로입니다.

의도한 동작입니다. 두 기능은 별도 창을 열며 현재 작업 화면을 유지합니다. 창 뒤에 가려진 경우 작업 표시줄 또는 열린 창을 확인하세요.

URL이 있는데 아직 검증된 항목이 아닙니다.

JS나 API 문서에서 발견한 URL은 실제 요청 성공을 뜻하지 않습니다. 활동 추적의 발견만 함, 요청 관측, 수동 완료를 나눠 확인하세요.

q 값을 바꿨는데 파라미터가 완료되지 않습니다.

변경 관찰은 값의 변화가 감지되었다는 뜻입니다. 실제 진단이 끝난 후 파라미터 완료를 누르세요. URL 완료도 별도로 관리합니다.

Repeater 초안을 눌렀는데 트래픽이 증가하지 않습니다.

초안 준비는 전송이 아닙니다. Repeater에서 값·인증을 확인하고 Send를 눌러야 요청이 발생합니다. 권한 비교, GET 검증, 페이로드 시작은 실제 요청을 보냅니다.

표에 HTTP 200 또는 경고가 있으면 취약점인가요?

상태 코드만으로 결론 내리지 않습니다. 공개 정책, 논리적 차단, 없는 경로 기준, 원본 응답과 판정 근거를 함께 확인하고 수동 재현하세요.

글자가 가려지거나 결과 열이 안 보입니다.

창 크기, 표의 가로 스크롤, 분할선을 조정합니다. 설정에서 배치를 바꾸거나 배치 초기화를 사용하세요. 그림의 원본 크기로 보려면 HTML 이미지를 클릭해 확대합니다.
