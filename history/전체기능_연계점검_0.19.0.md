# 커뮤니티 사이트 전체 기능 연계 점검 - Workbench KR 0.19.0

2026-10-11 / Community Security Lab 3.4.0 / Burp Suite Community 2026.7.3-52685

이번에는 사이트 정상 탐색부터 JS/API 발견, 환경/URL 검증, 계정·입력 검사, 업무 흐름 재현, 증거 보관, 커버리지 마무리까지 확장을 연결해 사용했습니다. 확장의 개별 기능은 동작하지만, 발견 후보와 실행 결과가 다음 단계로 전달되는 연결을 보강할 필요가 있습니다. 특히 동적 API 미확정 목록, 메서드·계정별 점검 상태, 페이로드 근거의 증거 연결이 중요합니다.

## 실행 범위

실제 Burp 런타임에 배포 JAR를 로드했습니다. 이번에는 임시 loopback 프록시 18288을 실행하고 실습 서버 18299에 정상 탐색 요청 6개를 보내 실제 Proxy History를 만들었습니다. 운영 브라우저 설정은 변경하지 않았습니다. Native Montoya API와 배포 JAR의 실제 Swing 컨트롤러·분석 엔진을 사용했으며 GUI 창은 열지 않았습니다.

이전 사용 시나리오 68개를 같은 실행에서 재수행하고, 전체 기능 연결 시나리오 83개를 추가했습니다. 총 151개 확인 항목이며 모두 기대 동작이 재현되었습니다. 이미 알려진 미흡점을 재현하도록 만든 항목도 포함하므로 “151개 확인 성공”은 결함이 없거나 수정됐다는 의미가 아닙니다.

배포 JAR 및 소스는 수정하지 않았습니다. 이번에는 실제 사용 범위를 넓혀 평가했습니다. 임시 Burp·프록시·콜백·사이트 프로세스와 검증용 브라우저 탭을 정리했습니다.

## 어떤 순서로 사용했는가

1. **트래픽·범위 준비**: Alice/Bob/moderator/admin으로 로그인합니다. 실제 프록시를 통해 홈·JS·API 문서·게시글 목록/상세·검색을 조회하고 트래픽 수집 및 SCOPE를 확인합니다.
2. **정상 데이터 이해**: URL/Base64/Hex/Gzip 변환 결과를 API 입력으로 사용합니다. 실제 발급 JWT의 필드·시간을 읽고 공개/비공개 게시글의 JSON 차이를 확인합니다.
3. **화면 밖 기능 수집**: 트래픽에서 JS 응답을 선택해 JS 추출로 전달합니다. 동적 경로를 구분하고 소스맵을 조회·복원합니다. 도메인·클라우드 URL·NPM 이름을 확인하며 NPM 조회는 외부 공개 레지스트리 대신 실습 서버의 로컬 레지스트리를 사용합니다. 수집 원본을 파일로 보관합니다.
4. **환경·URL 후보 확인**: 실제 Tomcat 응답을 관측하고 없는 경로 기준과 함께 설정 파일/API 후보를 선택 검증합니다. 실제 Burp History와 JS/OpenAPI를 URL 수집에 연결하고 200/404 경로 대표를 확인합니다.
5. **권한·입력 검증**: 게시글·쪽지·관리 API·첨부파일을 계정별로 대조합니다. 페이로드 16개 프로필을 각각 취약/수정 경로에 적용하고 정상/공격/대조 응답을 확인합니다.
6. **응답의 단서 연결**: Passive 헤더/오류 관찰, API 문서 메서드·템플릿, 저장/조회 마커를 확인합니다. HTML 출력과 이스케이프 출력 관측을 구분합니다.
7. **업무 흐름과 외부 근거**: 선택 요청을 Repeater로 준비하고 외부 입력 이름 TSV를 활동 추적으로 가져옵니다. 생성→조회→삭제를 순차 실행하고 JSON ID를 다음 단계에 연결합니다. OAST 메타데이터 가져오기와 증거 ZIP 저장을 확인합니다.
8. **누락 점검·보관**: 활동 추적에서 발견만 함과 미완료 항목을 확인합니다. 기록 JSON을 저장·복원하고 Excel 내보내기를 실행합니다.

## 전체 흐름에서 추가로 확인한 개선 항목

### W03. 동적 JS 후보를 끝까지 추적 - 높은 우선순위

실제 community.js는 17개 endpoint를 추출했으며 12개는 mode/객체 ID 등이 미확정입니다. JS 목록에는 보이지만 활동 추적은 complete가 아닌 endpoint를 전달하지 않습니다. 실제 요청을 임의로 보내지 않는 현재 제한은 유지해야 합니다. 대신 미확정 후보 자체를 별도의 발견 목록에 남기고, 실제 트래픽에서 `/api/community/fixed` 같은 공통 값을 선택해 관련 후보를 한 번에 확정하면 좋겠습니다.

변경 전: JS 목록에서 개별 후보를 기억하고 확정해야 합니다.
변경 후: 미확정 후보→값 확정→실제 요청→점검 완료의 상태를 같은 목록에서 볼 수 있습니다.

### W05. URL 하나에서 메서드·계정별 점검 상황 표시 - 높은 우선순위

`/api/community/fixed/posts`처럼 같은 URL을 GET과 POST가 공유합니다. URL 수집은 URL 키로 한 행에 합치고 OpenAPI POST 출처를 남기지만 실제 GET 확인의 HTTP 상태만 표시합니다. 활동 추적은 메서드별로 관리하므로 정보가 사라지는 것은 아니지만 화면 사이를 오가며 해석해야 합니다.

변경 전: URL 행의 HTTP 200은 GET 확인 결과이며 POST·다른 계정의 검증 상황은 별도로 봅니다.
변경 후: URL 요약에 GET 관측, POST 미점검, A/B/비로그인 확인 상태를 나란히 보여주고 해당 요청으로 이동합니다.

### W07. 페이로드 결과를 증거 묶음으로 연결 - 높은 우선순위

16개 프로필을 실행하고 취약/수정 쌍에서 후보 차이까지 확인했습니다. 현재 증거 묶음의 입력은 선택 트래픽·선택 권한 비교·업무 흐름입니다. 페이로드 결과의 기준/공격/대조 요청과 판정 근거를 한 번에 가져오는 연결이 없어 결과를 다시 정리해야 합니다.

변경 전: 검사 표의 결과와 별도의 증거 준비 작업을 연결합니다.
변경 후: 결과 선택→기준/공격/대조 패킷·원본 URL·프로필·판정 근거 추가→영향/절차 작성으로 진행합니다. 자동 후보를 확정 취약점으로 바꾸지는 않습니다.

### W09. 업무 단위 점검 목록 - 높은 우선순위

발견 근거는 JS/API/URL 수집, 실제 요청은 트래픽, 권한 판정은 History, 입력 검사는 페이로드, 증거는 점검 지원에 나뉩니다. 각 기능이 동작해도 “파일 다운로드 기능에서 무엇을 확인했고 무엇이 남았는가”를 한 번에 읽기는 어렵습니다.

변경 전: 기능 탭별 기록을 진단자가 연결합니다.
변경 후: 게시글·쪽지·파일·계정·관리 기능별로 관련 API, 계정, 입력, 검사 후보, 재검토, 증거 보관 위치를 연결한 점검 작업 목록을 제공합니다. 현재 탭 구조는 유지해도 됩니다.

### W08. OAST 상세 증거 연결 - 보통 우선순위 / 내보내기로 재현

수동 가져온 OAST ID는 표에 표시됐지만 증거 ZIP의 어떤 파일에도 해당 ID가 남지 않았습니다. 활동 추적의 DNS 검토 사유만으로는 ID·시각·원본 요청 대응을 대신할 수 없습니다. `oast.json`과 원본 요청 번호 연결을 추가하면 좋겠습니다. 이번 OAST 표 입력은 테스트용 메타데이터이며 실제 Pro Collaborator 결과가 아닙니다. 별도로 페이로드 SSRF의 실제 loopback HTTP 콜백은 성공했습니다.

### W04. 환경 탐색에 선택적 계정 대조 - 보통 우선순위 / 실행 동작 확인

환경 경로 검증은 비로그인 GET입니다. 익명 노출을 빠르게 찾는 데 적합합니다. 일반 회원과 관리자의 설정/API 노출 범위를 비교하려면 다른 탭에서 인증 요청을 다시 준비해야 합니다. 기본은 비로그인으로 유지하고 명시적으로 선택한 계정만 대조하는 기능이 있으면 좋겠습니다.

### W01. 원문 보관과 점검 기록의 차이를 표시 - 보통 우선순위 / 코드 확인

트래픽은 최근 250행·128KiB/행, URL 패킷은 300개, JS는 최근 100개 원본 등 보관 제한이 다릅니다. 활동 추적의 URL이 남아 있어도 같은 원문이 다른 탭에 남아 있다는 뜻은 아닙니다. 중요한 패킷 고정, 제외 사유, Burp 원문 또는 보관된 증거 위치를 표시하면 재현 준비가 쉬워집니다. 제한을 무조건 늘리는 것은 권장하지 않습니다.

### W02. 구조 비교의 중요 필드와 근거 전달 - 보통 우선순위 / 기능 구조 확인

공개/비공개 객체의 차이를 읽고 다음 차이로 이동하는 기능은 동작했습니다. 소유자·공개 범위·금액·역할처럼 진단 목적에 중요한 필드를 선택하거나 해당 차이를 증거 묶음에 직접 넣는 연결이 있으면 검토가 쉬워집니다. 이번 실습의 금액/역할 예는 기능 제안이며 실제 결제 업무 검증 결과가 아닙니다.

### W06. Passive 경고에 전체 영향 URL 보관 - 보통 우선순위 / 코드 확인

Passive 경고는 Origin·규칙·위치·근거로 합산합니다. 대표 URL 하나와 횟수만으로는 같은 경고가 어느 페이지에 있었는지 모두 확인하기 어렵습니다. 그룹 아래 영향 URL 목록과 첫/최근 응답 근거를 보관하고 증거 묶음으로 전달하면 좋겠습니다.

## 이전에 재현한 10개 항목과의 관계

권한 판정 충돌, 계정별 커버리지, 경로 ID 누락, 업무 흐름 본문 CRLF 변형, 소유 JSON 경로 미리보기, 일반 쿠키의 인증 후보 증가, 단계별 기대 조건, 폼/파일 증거, 폼 초안 Content-Type, 큰 파일의 권한 비교 제한을 이번 실행에서도 재현했습니다. 세부 재현과 완료 기준은 별도의 커뮤니티 실사용 점검 보고서에 있습니다.

이번 추가 9개는 주로 기능 사이의 연결·운영 제약입니다. 모두 새 버그 9개라고 분류하는 것은 부정확합니다. W03/W05/W08은 실제 결과로 확인했고 W01/W02/W06/W07/W09는 실행 과정과 코드 구조를 바탕으로 제안한 연결 개선입니다.

## 구현 권장 묶음

1. **정확성**: ALLOW/소유자 판정 충돌 및 본문 CRLF 변형을 먼저 수정합니다.
2. **발견 누락 방지**: 미확정 JS 후보·경로 ID·계정/메서드별 커버리지를 연결합니다.
3. **재현 준비**: 원본 Content-Type의 초안, 환경 계정 대조, 프로필 세트 전환을 제공합니다.
4. **근거 보관**: 페이로드/Passive/OAST/구조 비교의 선택 근거를 증거 묶음으로 연결합니다.
5. **전체 점검 관리**: 기능별 진행 상황·재검토·원문 보관 위치를 업무 단위 목록으로 모읍니다.

## 외부 기능과 미검증 범위

- Param Miner/InQL/Turbo Intruder의 안내·Repeater 준비·TSV 가져오기는 확인했습니다. 해당 BApp의 실제 설치 및 검사 실행은 이번에 수행하지 않았습니다.
- NPM 조회는 이름만 전달하는 자체 로컬 레지스트리로 확인했습니다. 외부 NPM 등록 상태를 진단한 것이 아닙니다.
- SSRF는 실습 서버가 요청한 실제 loopback HTTP 콜백으로 확인했습니다. Pro Collaborator 외부 연결·DNS 콜백 검증과는 별도입니다.
- XSS는 반사/저장/조회 및 출력 처리 차이까지 확인했습니다. 실제 브라우저 JS/DOM 실행은 인앱 브라우저의 localhost 접속 타임아웃으로 완료하지 못했습니다.
- 16개 프로필 중 LDAP/NoSQL/command/일부 헤더 사례는 제한된 실습 fixture입니다. 외부 디렉터리/DB/OS 명령 시스템에 대한 검증 결과로 확대하지 않습니다.
- 실제 GUI의 마우스 조작, 다중 창 위치/반응 속도, TLS/HTTP2, 전체 Docker/Oracle/Nginx 환경은 평가하지 않았습니다.

총 기능을 최대한 연결해 사용하는 흐름은 확인했으며, 미검증 항목은 위 범위에 남습니다.
