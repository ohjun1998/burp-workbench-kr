# 커뮤니티 사이트 대상 확장 실사용 점검 - 0.19.0

2026-10-11 / Burp Workbench KR 0.19.0 / Community Security Lab 3.4.0

점검 결과, 일반 탐색·JS/API 수집·계정별 교차 요청·취약/수정 경로 대조는 활용 가능했습니다. 다음 배포에서는 판정 규칙 충돌, 계정별 커버리지, 본문 원형 보존을 먼저 개선하는 것이 좋겠습니다. 아래 10개는 확장에서 재현한 동작 또는 기능 제약이며 서비스 취약점 10개를 발견했다는 의미는 아닙니다.

## 실행 방식과 근거

- 설치된 실제 Burp Suite Community 2026.7.3-52685 런타임에 기존 배포 JAR를 로드했습니다. native Montoya API로 실제 HTTP를 전송하고 배포 JAR의 권한 비교·활동 추적·업무 흐름·증거 생성 코드를 사용했습니다.
- Alice/Bob/moderator/admin 계정으로 로그인하고 게시글·검색·쪽지·사용자 목록·첨부파일을 정상 탐색했습니다. 이후 다른 계정으로 읽기 권한을 비교하고, 내 실습 객체를 생성·업로드했습니다.
- 이번 추가 사용 시나리오는 68개 확인 항목을 수행하여 아래 동작을 재현했습니다. 결함을 재현하도록 설계된 검사도 있으므로 68개 확인 성공은 결함 수정 완료를 뜻하지 않습니다.
- 기존 전 기능 연계 검사도 새로 실행했습니다: 100개 검사 통과, 실제 HTTP 199회, 16개 페이로드 프로필의 취약/수정 쌍 포함.
- 별도 GUI 창·프록시 리스너를 열지 않은 headless 실행입니다. 사람의 마우스 클릭과 화면 전환 속도를 평가한 GUI 사용성 시험은 수행하지 않았습니다. 별도의 클라우드 가상 머신은 사용하지 않았습니다. 임시 실습 서버와 Burp 프로세스는 종료했습니다.
- 배포 JAR SHA-256은 이전 배포와 일치합니다. 이번 결과는 개선 분석이며 배포 소스/JAR 수정본은 생성하지 않았습니다.

P1은 다음 배포에서 우선 처리할 품질 문제입니다. 보안 취약점의 심각도 등급이나 CVSS를 부여한 것은 아닙니다.

### A01. 기대 ALLOW와 소유자 전용 판정 충돌 - P1 / 실제 Burp에서 재현

Bob의 비공개 게시글에 admin이 접근하는 것은 실습 사이트 정책상 허용됩니다. 관리자 슬롯의 매트릭스를 ALLOW로 지정했지만 기존 소유자 전용 정책은 유지한 상태에서 실행하니 다음 두 판정이 한 결과에 함께 나타났습니다.

> 기대 ALLOW · 성공 응답 관측 · 타인 객체 접근 의심 · 소유자 전용 정책 · 소유 필드가 대상 계정 소유값과 다름

매트릭스 결과를 기존 결과 앞에 붙이는 구조 때문입니다. 관리자·게시판 관리자·공유 객체가 많은 실제 진단에서는 정상 접근도 위반 후보가 되어 검토 시간이 늘어납니다.

개선: 메서드/경로/계정의 명시적 기대 정책을 최종 판정의 기준으로 사용하고 기존 소유자 차이는 보조 근거로 분리합니다. 서로 모순된 설정은 실행 전에 경고합니다. ALLOW라도 실제 허용 데이터 범위까지 자동 확인된 것으로 표시하면 안 됩니다.

완료 기준: ADMIN ALLOW는 소유자 불일치만으로 위반 후보가 되지 않고, Alice DENY의 실제 데이터 반환은 위반 후보로 유지되어야 합니다. 소스 근거: AuthComparePanel.java:99.

### A03. 계정별 커버리지와 완료 상태 재점검 - P1 / 실제 Burp에서 재현

Alice의 `/search?q=Burp`를 관측하고 URL을 수동 완료한 뒤 Bob의 `/search?q=Burp&page=2`를 관측했습니다. 새 `URL:page`는 미점검인데 URL 행은 여전히 점검 완료였습니다. 기록 키에는 계정/역할이 없어 Alice·Bob의 점검 상태도 하나로 합쳐집니다. 현재 URL 완료와 파라미터 완료가 독립적인 것은 의도된 동작이지만 전체 점검률로 읽기에는 설명이 부족합니다.

개선: 계정 별칭·역할·입력 위치와 진단 종류를 커버리지에 추가합니다. 인증값 원문을 저장하지 않고 사용자가 지정한 프로필 이름으로 연결합니다. 새 입력이 추가되면 “추가 입력 미점검” 또는 “재검토 필요”를 표시하고, URL 완료 표시 옆에 남은 계정/입력 검사 수를 보여줍니다.

완료 기준: Alice 완료와 Bob 미점검을 동시에 표현하고, 새 파라미터가 생겨도 기존 근거는 보존하면서 재점검 항목을 구분해야 합니다. 소스 근거: ActivityTracker.java:13, 21, 50.

### A04. 경로 객체 ID를 파라미터 목록에 포함 - P1 / 실제 Burp에서 재현

`/posts/102`를 Repeater 요청으로 관측해도 파라미터 목록에 `PATH:id`가 없습니다. URL 행은 남아 있으므로 요청 자체가 누락된 것은 아닙니다. 하지만 게시글·쪽지·파일 다운로드의 ID 변경 검사가 파라미터 단위 미점검 목록에서 빠집니다.

개선: 관측한 OpenAPI의 `{id}`와 실제 경로를 연결해 `PATH:id`를 추가합니다. 문서가 없으면 숫자/UUID 구간을 경로 변수 후보로 표시하고 진단자가 확정하도록 합니다. 같은 패턴 아래 객체별·계정별 실제 요청 근거를 보존합니다.

완료 기준: `/posts/101`, `/posts/102`를 하나의 업무 경로로 묶어도 각각의 객체 접근 기록은 확인할 수 있어야 합니다. 소스 근거: ActivityTracker.java:35 및 ApiInventory.Endpoint의 경로 템플릿.

### A06. 업무 흐름의 본문 CRLF 원형 보존 - P1 / native 요청 생성에서 재현

본문 `FIRST\r\nSECOND`를 업무 흐름 요청으로 준비하니 `FIRST\nSECOND`가 되었습니다. 입력 13바이트가 출력 12바이트로 바뀝니다. 이 확인은 실제 Burp 요청 객체 생성으로 수행했으며 해당 변형 요청은 서버에 전송하지 않았습니다.

전체 raw 요청에서 CRLF를 LF로 바꾼 뒤 본문을 다시 넣는 구조입니다. 텍스트 업로드·서명된 본문·multipart에서는 진단자가 준비한 요청과 다른 바이트가 나갈 수 있습니다.

개선: 헤더와 본문을 먼저 나누고 헤더 부분만 정규화합니다. 본문은 변수 치환 대상으로 명시된 부분 외에는 원형을 유지하며 Content-Length를 실제 전송 바이트로 계산합니다. UI에서 본문 변형 여부를 미리 확인할 수 있게 합니다.

완료 기준: LF/CRLF 텍스트, multipart 경계, UTF-8 입력을 그대로 유지하고 기존 단계 구분·변수 치환 테스트도 통과해야 합니다. 소스 근거: BountyWorkflow.java:19.

## 이어서 개선할 부분

### A02. 소유 JSON 경로 미리보기 - P2 / 실제 Burp에서 재현

커뮤니티 메인 API는 `OWNER_ID`를 반환하지만 `$.ownerId`를 입력하면 해당 경로가 없다는 사전 경고 없이 일반 동일 응답 비교로 돌아갑니다. 판정은 “우회 의심”으로 남았으므로 이번 사례가 검출되지 않은 것은 아니지만 사용자는 설정 오류를 알아차리기 어렵습니다.

개선: 원본 JSON을 기준으로 지정 경로의 실제 값과 경로 없음 상태를 표시합니다. 권한 정책이 소유자 기반일 때 값 미검출은 판정 보류 근거로 명시합니다. 계정의 신원 JSON과 대상 객체 소유 JSON을 별도 항목으로 안내합니다.

### A05. 일반 쿠키 변화로 인증 후보 증가 - P2 / 실제 Burp에서 재현

동일 Alice JSESSIONID에 `loop_hint=one`만 추가해도 인증 후보가 2개가 됐습니다. 쿠키 전체가 인증 지문에 포함됩니다. 실제 서비스의 테마·분석·A/B 테스트 쿠키가 바뀌면 계정을 고르기가 불편해집니다.

개선: 인증 쿠키 이름을 선택하고 부가 쿠키는 별도로 유지합니다. 같은 신원이라고 사용자가 확인한 후보는 프로필로 연결할 수 있게 합니다. 값이 비슷하다는 이유만으로 자동 병합하지 않습니다.

### A07. 업무 흐름의 기대 결과 검증 - P2 / 실제 Burp에서 재현

검색 결과가 `[]`인 HTTP 200도 “관측 완료 · 최종 상태 수동 확인”으로 표시됩니다. 현재 표시는 취약점 확정이 아니라 관측 상태이므로 오류 판정은 아닙니다. 다만 생성·승인·수정·중복 처리 등을 반복 점검할 때 조건을 매번 직접 확인해야 합니다.

개선: 단계별 기대 HTTP, 필수 JSON 경로, 기대 값, 본문 포함/제외와 최종 상태 검사를 선택적으로 설정합니다. 관측 완료와 조건 충족을 분리하고 조건 실패 시 후속 진행 여부를 선택하게 합니다. 쿠폰·결제·동시성은 이 사이트에서 실제 재현한 사례가 아니며 향후 적용 예입니다.

### A08. 폼·파일 증거 저장 보완 - P2 / 실제 ZIP 생성에서 재현

정상 게시글 생성에 사용한 form 본문은 본문 포함 옵션을 켜도 ZIP에서 “[비 JSON 본문 제외]”로 대체됐습니다. JSON만 포함하는 현재 설계에 따른 제약입니다. 폼 요청이나 업로드 증거를 보고서만으로 재현하려면 로컬 원본을 찾아야 합니다.

개선: 기본 가림을 유지하면서 form 항목별 가림과 명시적 선택 저장을 지원합니다. multipart는 파일명·MIME·크기·해시와 선택한 실습 파일 첨부로 처리합니다. 각 항목에 “재현에 필요한 원문 누락” 표시와 로컬 근거 참조를 추가합니다. 소스 근거: BountyEvidence.java:12.

### A09. 활동 추적 초안의 본문 형식 - P2 / 실제 HTTP로 재현

같은 게시글 생성 API에서 캡처한 form 요청은 200이었지만, 활동 추적용 공통 초안으로 올바른 필드 값을 JSON에 넣어 보내니 400이었습니다. 공통 초안은 BODY 이름을 JSON으로 구성하고 Content-Type을 application/json으로 설정합니다. 응답 분석의 OpenAPI 초안은 문서 Content-Type을 보존하므로 이 문제와 구분됩니다.

개선: 요청 Content-Type 및 문서 입력 구조를 메타데이터에 보관하고 form/JSON/XML을 선택하게 합니다. 이미 관측한 요청이 있으면 인증값을 가린 원본 구조에서 초안을 준비합니다. 인증과 REPLACE_ME 값은 진단자가 채우도록 유지합니다. 소스 근거: JsRequestDraft.java:8 및 ActivityPanel.draftSelected.

### A10. 큰 첨부파일 권한 비교 - P2 / 실제 업로드·다운로드로 확인

사이트에서 140,000바이트 TXT 파일을 정상 업로드하고 200으로 다운로드했지만, 확장의 권한 비교는 요청+응답 128KiB 제한 때문에 비교 대상으로 받을 수 없었습니다. 사이트는 최대 1MiB를 지원합니다. 메모리 제한은 필요하지만 일반 첨부파일 점검 범위가 줄어듭니다.

개선: 전체 본문을 무제한 보관하지 않고 상태·헤더·길이·스트리밍 해시 및 제한된 구간을 비교하는 파일 전용 모드를 추가합니다. 응답 앞부분만 같다고 동일 파일을 확정하지 않습니다. 제외된 요청은 활동 추적에 사유와 대체 수동 확인 절차를 표시합니다. 소스 근거: AuthComparePanel.java:12, 62.

## 코드에서 확인한 추가 운영 제약

아래는 이번 사이트에서 기능 동작을 실증한 10개 항목과 구분되는 코드 검토 결과입니다.

1. 계정 슬롯이 3개입니다. Alice/Bob/비로그인을 유지하면서 moderator/admin까지 비교하려면 슬롯을 다시 지정해야 합니다. 계정 프로필 목록과 비교 세트 저장/전환이 있으면 편리합니다. 근거: AuthComparePanel.java:17.
2. OAST 표의 ID·시각·원본 요청 연결은 증거 ZIP의 별도 구조화 파일에 포함되지 않습니다. 활동 추적에는 검토 사유가 연결되지만 전체 콜백 상세를 대체하지 못합니다. `oast.json` 및 관련 요청 파일 연결을 추가하면 보고서 정리가 쉬워집니다. 근거: BountySupportPanel의 correlations/oastModel, BountyEvidence.java:26.
