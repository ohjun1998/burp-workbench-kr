# 커뮤니티 사이트 대상 확장 진단 검토 — Workbench KR 0.17.4

실제 커뮤니티 서버의 취약/수정 구현을 비교해 **SQL 조건 비교 미탐, 공개 객체 권한 후보의 잡음, JS 구문 분석 실패**를 우선 개선 대상으로 확인했습니다. 다음 단계는 이 세 부분을 먼저 수정하고, 환경 기준 응답·404 차단 분류·URL 수집을 다듬는 것이 효과적입니다.

## 검증 범위

- 대상: 첨부 프로젝트의 LOOP 커뮤니티 실습 사이트 3.3 소스. Spring MVC/Tomcat/H2를 `127.0.0.1:18099`에서 임시 실행했습니다. 서버는 검증 후 종료했고 해당 포트의 리스너가 없는 것을 확인했습니다.
- 실행 코드: 기존 **0.17.4 배포 JAR**의 `Engine`, `Adaptive`, `AuthJudgement`, `AuthComparePanel`, `JsAnalysis`, `JsMiner`, 환경 비교·URL 패턴·활동 추적 코드. JAR의 SHA256이 앞선 릴리스와 같은 것을 확인했습니다.
- 방식: 실제 HTTP 요청/응답을 사용했습니다. 권한 비교 패널은 headless Swing과 Montoya API 어댑터를 통해 실제 서버로 재전송했습니다. Burp GUI/프록시를 실제로 로드한 통합 검증은 아닙니다. 클라우드 VM 또는 Docker/Oracle 스택에서 실행한 결과도 아닙니다.
- 계정: 비회원·Alice·Bob·운영자·관리자. 글·쪽지·첨부·관리자 접근을 취약/수정 경로에서 비교했습니다.
- 완료: 사이트 기본 검사 49개, 확장 연계/현상 재현 76개, HTTP로 가져온 JS 샘플 회귀 62개. 합계 **187개 검사**를 완료했습니다. 보조 재현으로 SQL 정규화·HTML 경로 표시·도메인 추출·6개 구문 유형도 확인했습니다. 최종 확장 연계 실행에서 HTTP **139건**을 보냈으며 별도 사이트 기본 검사의 HTTP 요청은 이 수에 포함하지 않습니다.

검사 통과는 **현재 동작과 문제의 재현을 확인했다**는 뜻입니다. 아래 미탐과 검토 잡음까지 정상이라는 의미가 아닙니다. 이번 단계에서 운영 확장 소스/JAR을 변경하지 않았으며 진단 하네스와 근거를 추가했습니다.

## 주요 재현 근거

### A01 — SQL 조건 비교 미탐

`/api/community/vuln/search?q=Burp`의 안정된 기준 응답과 참 조건 응답은 본문 SHA256까지 같고, 거짓 조건 응답은 빈 배열입니다. 그런데 고정/적응형 모두 거짓 조건을 '응답 변화'로만 남깁니다.

```text
기준: Burp                       → 200 / 152자
참:   Burp%' AND 1=1 --          → 200 / 152자 (기준과 동일)
거짓: Burp%' AND 1=2 --          → 200 / 2자   ([])
```

`Engine.normalized`는 본문 어디에 있든 입력값을 제거합니다. 기준 응답의 정상 게시글 제목 `Burp Proxy ...`에서는 `Burp`가 제거되지만 참 응답에는 긴 페이로드 문자열이 없어 제목이 그대로 남습니다. 그 결과 같은 본문을 서로 다르다고 비교합니다. `Adaptive.pair`도 같은 함수를 사용합니다.

원본 응답 동일성 비교를 먼저 적용하고, 반사 제거는 실제 반사 위치를 확인한 경우에만 적용하는 것이 우선입니다. 참/거짓 반복과 응답 변화의 원인도 함께 기록해야 합니다. 입력값을 광범위하게 삭제하거나 참/거짓 차이만으로 SQLi를 확정하는 방식은 피합니다.

소스: `kr/payloadrunner/Engine.java:140`, `Adaptive.java:50` 및 `:51`.

### A02/A05 — 공개 정책과 404 은닉 정책

수정 경로 `/api/community/fixed/posts/101`은 비회원도 읽는 공개 글입니다. 계정이 달라도 본문이 같아 일반 비교에서는 '우회 의심'이 되고, `$.OWNER_ID`와 Bob 소유값 `2`를 설정하면 '타인 객체 접근 의심'이 됩니다. 실제 권한 비교 패널에서도 재현했습니다. 이는 취약점 확정이 아닌 의심 분류지만 검토량을 늘립니다. 공개 글 작성자와 조회자 ID가 다르다는 사실만으로 인가 위반을 판단할 수 없습니다.

반대로 비공개 `/posts/102`는 Bob에게 200, Alice에게 404이며 정책상 올바른 차단입니다. 현재는 판정 보류입니다. 원본 소유자 응답과 재조회가 모두 200인지 확인한 뒤 '은닉형 접근 차단 후보'로 별도 분류하면 좋습니다. 존재하지 않는 객체, 삭제/동시 변경 등과 구분해야 하므로 모든 404를 차단으로 처리하면 안 됩니다.

소스: `kr/workbench/AuthJudgement.java:14`, `:18`, `:25`. 경로/메서드별 정책은 현재 규칙에 없는 추가 기능입니다.

### A03/A06 — 실제 커뮤니티 JS의 분석 한계

HTTP로 가져온 `community.js`는 AST 실패 1회, URL/API 15개, 전부 메서드 `?`입니다. URL 수집용 발견 결과 13개에는 실제 `/api/community/{mode}/posts`를 만들기 위한 문자열 `/posts`가 Origin 루트 `/posts`로 들어갑니다. 함수 `apiPath`와 `call`의 결합 관계가 사라져 경로·메서드·본문 메타데이터가 손실됩니다.

최소 구문 실험에서 **async/await와 ES module**은 실패했습니다. **optional chaining, nullish coalescing, object spread**의 단일 실험은 지원됐으므로 이 구문 전부가 미지원이라고 단정하면 안 됩니다. 기존 14종 JS 샘플의 62개 검사가 통과하더라도 실사용 코드 전체의 분석 완전성을 보장하지 않습니다.

또 `community.js`의 도메인 후보 72개에는 `document.querySelector`, `opt.method`, `JSON.parse` 같은 속성 접근이 포함됩니다. 최소 코드에서도 `user.role`, `window.fetch`, `json.parse`가 호스트로 표시됩니다. 확실한 URL/문자열 호스트와 낮은 신뢰도 후보를 분리할 필요가 있습니다.

소스: `kr/workbench/JsAnalysis.java:33`, `JsMiner.java`의 도메인 추출. JS를 실행하지 않는 제한적 정적 분석과 미해결 표시를 유지하는 방향을 권합니다.

### A04 — 환경 기준의 HTML 경로 인코딩

Tomcat은 없는 경로 메시지를 `No endpoint GET &#47;audit-missing-one.`처럼 출력합니다. 두 기준 페이지는 이 경로 부분 외에는 같습니다. 현재 정규화는 원본 `/audit-missing-one`을 찾기 때문에 `&#47;`로 표시된 문자열을 제거하지 못합니다. 결과적으로 '.env 미발견' 등 모든 행에 기준 불안정 메시지가 붙습니다.

알려진 요청 경로의 HTML entity/percent 표현만 비교용 서명에서 정규화하고, 원본 패킷은 유지해야 합니다. HTML 전체를 임의로 수정하거나 모든 숫자/문자열을 삭제하는 방식은 필요한 차이를 없앨 수 있습니다.

소스: `kr/workbench/EnvironmentResponse.java:8`.

### A07/A08 — 수집 완료와 진단 커버리지 분리

`posts/101`과 `posts/102`는 같은 GET 패턴으로 묶이지만 비회원 응답은 200/404로 다릅니다. 대표 1개 확인은 경로 패턴의 확인일 뿐 모든 객체의 권한 확인이 아닙니다. 지금도 활동 추적 완료 표시는 별개지만, 대표 창에서도 미검증 객체 개수와 서로 다른 접근 상태를 강조하면 누락을 줄일 수 있습니다. 숫자/UUID 경로 인자의 객체 접근 분류도 추가할 가치가 있습니다.

`/v3/api-docs`의 실제 OpenAPI 응답은 현재 발견 함수에서 0개입니다. 별도 OpenAPI 파서로 경로/메서드/인자 이름을 수집하되 템플릿 `{id}`를 그대로 유지해야 합니다. **실습 사이트 문서 자체에도 댓글·수정·삭제 등 일부 POST 경로를 GET으로 적은 오류가 있습니다.** 문서와 실제 관측 메서드가 다르면 경고해야 하며 문서만 믿고 요청을 자동 전송하면 안 됩니다.

소스: `kr/workbench/ReconMetadata.java:24`, `:43`; 실습 사이트 `LabController.java`의 `docs()`.

### A09/A10 — 지원 범위의 확장

저장형 댓글 검사에서는 POST 응답이 JSON이고 별도 GET에서 저장 문자열이 보였습니다. 현재 반사형 XSS 엔진이 이를 HTML XSS로 판정하지 않은 것은 보수적인 동작입니다. 실습 프런트엔드의 취약 모드는 댓글을 원문 HTML로, 수정 모드는 escape 후 넣도록 구현됐습니다. 이번에는 브라우저에서 스크립트 실행을 확인하지 않았습니다. 쓰기→조회→출력 맥락을 묶는 지원을 추가하되 저장/반사 후보와 실행 입증을 구분해야 합니다.

이 프로젝트의 `PassiveScanPanel`은 현재 URL 수집과 GET 확인 기능입니다. 실제 응답 기반 취약점 스캐너와 같은 지원 범위로 보기는 어렵습니다. 코드 검토에서 별도 ScannerCheck 등록/응답 보안 규칙은 찾지 못했습니다. 수집·활동 추적에 기존 응답의 오류/민감 정보/쿠키/헤더 관찰을 연결하면 유용하지만, 이는 이번에 실행해 검증한 탐지 기능이 아닌 **추가 구현 제안**입니다.

## 권장 구현 순서와 재검증 기준

1. **SQL 비교 수정:** 이번 152자/2자 사례를 후보로 잡고, 수정 구현·단순 반사·WAF 차단·불안정 기준의 기존 음성 검사를 함께 통과시킵니다.
2. **권한 정책 추가:** 공개 101은 허용 접근, 비공개 102의 취약 접근은 의심, 수정 404는 존재 근거를 둔 차단 후보로 분리합니다. 원본 소유자 응답·계정 이름·당시 정책을 이력에 저장합니다.
3. **JS 분석 보완:** 실제 community.js와 async/module 샘플에서 메서드/래퍼 경로를 보존하고, 미확정 문자열을 실행 가능한 완성 경로로 취급하지 않습니다. 기존 시크릿 가림·Source Map·시간/크기 제한도 재검증합니다.
4. **환경·URL 보완:** 인코딩된 경로 차이만 같은 기준으로 묶고, 진짜 동적 본문은 불안정으로 남깁니다. 서로 다른 접근 상태의 대표와 객체별 완료 여부를 확인합니다.
5. **문서/수집 흐름 보완:** 실습 OpenAPI 메서드를 고치고, 수집 파서가 문서 오류를 관측 트래픽과 구분하는지 검증합니다. 저장형 흐름과 응답 Passive 규칙은 별도 기능으로 확장합니다.

## 근거 파일

같은 이름의 `_결과.json`에는 HTTP 분류, 판정/본문 해시, JS 분석, 보조 재현, 검사 항목이 담겨 있습니다. `_사례.csv`에는 비교 사례를 요약했습니다. `_재현코드.zip`에는 이번 하네스·실행 스크립트·로그·실행 안내가 있습니다. 실제 계정 세션 Cookie는 결과 파일에 저장하지 않았습니다. 실습용 JWT 디코딩과 가림 처리된 시크릿 후보만 포함합니다.
