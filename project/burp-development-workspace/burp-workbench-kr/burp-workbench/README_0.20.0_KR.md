# Burp Workbench KR 0.20.0 — 개선사항 및 검증

기존 0.19.0에서 재현했던 문제를 수정·보완하고 전체 기능을 다시 점검했습니다. JAR와 소스는 0.20.0으로 배포합니다. 기존 0.19.0 배포 파일은 과거 버전으로 보존했습니다.

## 변경 전 / 후

| 대상 | 변경 전 | 0.20.0 |

| 완료 후 변경 A03 | 새 입력/인증 조건이 추가되어도 URL 완료 상태 유지 | 완료 이력 플래그를 보존하면서 재검토 필요 표시. 복원 후 인증 조건도 재확인 |

| 인증 후보 A05 | 일반 쿠키 변화로 후보가 증가 | 사용자가 식별 쿠키 이름을 선택 가능. 식별과 전송을 구분하여 전체 세션 쿠키는 유지 |

| 폼 증거 A08 | JSON 포함 옵션으로도 폼 본문 제외 | JSON/폼 명시적 포함. 민감 키·알려진 인증값 가림, 중복 폼 필드 유지. 파일 원문은 계속 제외 |
| 활동 초안 A09 | 항상 JSON으로 생성해 폼 API에서 400 | 관측한 JSON/폼 Content-Type 유지. Multipart 등 미지원 형식은 실제 요청 사용 안내 |
| 대용량 응답 A10 | 128KiB 초과 파일 비교 제외 | 명시적 최대 4MiB 옵션, 전체 응답 본문 바이트 수·SHA-256 비교. 동일 접두부/부분/빈 응답을 접근 증거로 확정하지 않음 |
| JS 발견 W03 | 동적 API가 활동 추적에서 사라짐 | 미확정 JS 발견 탭에 보관, 소스 근거 이동, 같은 Origin/SCOPE에서 수동 확정, JSON/Excel 내보내기 |

| OAST 증거 W08 | 콜백 표 ID/시각이 ZIP에 없음 | oast.json 포함, URL/메서드 기준 증거 요청 번호 연결. 연결만으로 콜백 원인을 확정하지 않음 |

## 추가 경계 점검에서 보완한 부분

- 원본과 같은 인증으로 보낸 비교는 매트릭스로 덮어쓰지 않고 교차 인가 미검증을 유지합니다.
- 실제 전송 Origin·경로·쿼리·메서드가 변경되면 권한 판정과 업무 흐름을 보류/중단합니다. Burp 규칙으로 다른 요청이 전송된 결과를 원래 요청에 귀속하지 않습니다.
- 응답 변수 추출 실패는 해당 단계에 실패로 기록합니다. 관측 완료로 남아 증거에 들어가는 문제를 방지했습니다.
- token 등의 이름을 가진 인증 쿠키를 쿼리/본문 인증값으로 잘못 제외하지 않습니다.
- OAST 외부 결과의 잘못된 시각을 전체 가져오기 전에 거부합니다.
- JSON/폼에 반사된 짧은 인증값도 값 전체가 일치하면 가립니다.
- 증거의 요청/응답 **텍스트 미리보기 해시**와 대용량 응답의 **실제 본문 바이트 해시**를 구분합니다. 가린 패킷은 그대로 재전송할 원본 HTTP 바이트가 아닙니다.

## 새 기능 사용 순서

1. Burp Extensions에서 이전 Workbench를 해제하고 `burp-workbench-kr-0.20.0.jar`를 Java 확장으로 로드합니다. 트래픽 우클릭 → SCOPE 지정으로 점검 범위를 정합니다.
2. 권한 비교 → 비교 설정에서 ‘인증 후보 식별 쿠키 이름’에 예를 들어 `JSESSIONID`를 입력하고 쿠키 설정 적용을 누릅니다. 이후 들어오는 트래픽에서 후보를 재수집해 계정 슬롯을 지정합니다. 빈 값은 이전처럼 모든 쿠키로 구분합니다.
3. ‘세션·권한 매트릭스’에 `GET /api/posts/{id} DENY ALLOW UNKNOWN`처럼 계정별 기대 정책을 입력합니다. 같은 인증으로 재전송한 결과나 실제 대상 변경은 기대 정책으로 덮어쓰지 않습니다.
4. 활동 추적 → ‘미확정 JS 발견’에서 대상과 소스를 확인합니다. 확정 URL을 입력하고 ‘확정 URL → 발견 목록’을 누르면 발견으로 이동합니다. 요청을 자동 전송하거나 점검 완료로 만들지 않습니다.
5. 활동 추적에서 URL 완료 후 새 입력/인증 조건이 들어오면 재검토 필요가 표시됩니다. 숫자/UUID PATH 후보도 수동으로 확인합니다. 이 경고는 사용자 계정을 자동 식별한 결과가 아닙니다.
6. 환경 탐색 → 도구 설정의 후보 설정 → 검증 계정에서 비로그인 또는 지정 계정을 고릅니다. 세션 갱신이 필요한 계정은 권한 비교에서 먼저 확인합니다. 선택한 계정 조건을 각 실행에서 비교해야 하며 한 번에 모든 계정을 자동 실행하지 않습니다.
7. 권한 비교 → 비교 설정 → ‘대용량 응답 해시 비교’를 켜면 최대 4MiB 응답을 비교합니다. 내용 전체 해시가 같더라도 정책·영향을 확인해야 하며 206/빈 응답은 판정 보류입니다. History 본문 보관은 합계 32MiB 기준으로 오래된 기록을 정리합니다.
8. 점검 지원 → 업무 흐름 → 대상 설정에서 기대 조건을 설정합니다. 예: `1.HTTP=200`, `2.$.state=READY`. 응답 변수 추출 규칙은 기존의 별도 입력을 사용합니다. 조건 일치는 지정한 조건의 일치이며 업무 전체나 취약점 입증이 아닙니다.
9. 페이로드 검사에서 검사 종료 → 결과 선택 → 더보기 → ‘검사 결과 → 증거 묶음’. 기준·대조를 함께 가져와 점검 지원에서 실제 영향과 재현 절차를 작성합니다. 한 검사 32개/전체 증거 32개 한도를 확인합니다.
10. OAST 결과를 가져올 때 ISO 시각을 사용합니다. 예: `event-01 [탭] HTTP [탭] 2026-10-11T00:00:00Z [탭] GET [탭] https://대상/api/check`. 증거 ZIP의 oast.json에서 연관 요청 번호와 ID·시각을 확인합니다.
11. 폼/JSON 본문이 필요하면 증거 묶음의 포함 옵션을 선택하고 가림 결과를 검토합니다. 파일 원문/Multipart는 ZIP에서 제외되므로 필요한 경우 로컬 원본과 별도 증거로 보완합니다. 활동 추적 Excel에는 미확정 JS 목록도 포함됩니다.

## 검증 결과

- API 어댑터·headless Swing **848개 / 30개 검사군** 통과. 신규 회귀 검사 49개를 포함합니다.
- 페이로드 엔진 HTTP fixture **127개** 통과.
- 커뮤니티 실습 사이트 실제 HTTP 검사 **100개 / 199회 요청** 통과.
- 실제 **Burp Suite Community Edition 2026.7.3-52685**에 최종 JAR 로드. 수정 시나리오 **71개**, 전체 기능 흐름 **87개**, 합계 **158개** 확인 통과. 16개 페이로드 프로필의 취약/차단 대조군과 실제 loopback SSRF 콜백을 검증했습니다.
- 실제 프록시 History를 출발점으로 트래픽/SCOPE, 데이터 변환·JWT·구조 비교, JS·소스맵·의존성, 환경 탐색, URL 수집, 권한 비교, Passive/API/저장조회, 페이로드, 업무 흐름/OAST/증거, 활동 기록 저장·복원을 확인했습니다.
- 확장 오류 로그 **0바이트**. Headless Burp 자체의 Swing 테마 경고는 남았습니다.
- 전체 검사군 합계 **1233개**입니다. 서로 연관된 회귀·기능 확인이며 독립 취약점 수가 아닙니다.
- 테스트 리스너/서버 포트 18099, 18288, 18299, 18499, 19112 종료 확인. 임시 프로필을 사용했고 사용자 프록시/브라우저 설정을 변경하지 않았습니다. 클라우드 VM은 사용하지 않았습니다.
