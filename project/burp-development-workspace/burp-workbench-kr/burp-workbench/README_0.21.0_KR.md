# Burp Workbench KR 0.21.0 — 계정별·업무별 점검 사용법

활동 추적에 **계정별 점검**과 **업무별 현황**을 추가했습니다. 0.20.0의 기존 개선 사항을 유지하며, 서로 다른 계정의 완료 상태를 구분하고 발견·검사 시도·증거 저장·수동 완료·재검토를 업무별로 연결합니다.

## 변경 전 / 후

| 대상 | 0.20.0 | 0.21.0 |
|---|---|---|
| 점검 현황 | URL 중심 전체 현황 | 별도 계정 ID × 메서드 × URL 현황과 입력 완료 상태 |
| 계정 구분 | 인증 조건 변화 경고 | 진단자가 이름·역할·조직·Origin을 등록하고 선택 세션을 명시적으로 연결 |
| 완료 처리 | 전체 URL 완료 | Alice의 URL 완료와 Bob의 완료를 독립 관리. 기존 전체 완료는 계정 완료로 복제하지 않음 |
| 업무 관리 | 결과를 여러 도구에서 확인 | 업무에 요구 계정과 API를 연결하고 전체 요구 조합의 완료·재검토·증거 상태 표시 |
| 증거 | 준비·저장 과정과 진행 현황 분리 | 실제 ZIP 저장 성공 후 연결된 계정/API와 업무에 저장 기록 반영 |
| 완료 후 변경 | URL 재검토 경고 | 새 입력·새 업무 대상·계정 완료 해제·문제 있는 검사/갱신 실패 시 관련 업무도 재검토 |
| 계정 전환 | 슬롯의 계정과 점검 현황 연결 없음 | 슬롯을 다른 세션으로 바꾸면 기존 점검 계정 연결 해제. 명시적 재선택 필요 |
| 저장·복원 | 활동 메타데이터 JSON | 버전 3 계정·업무·이력 저장. 버전 1/2도 읽되 계정 기록을 임의로 생성하지 않음 |
| Excel | 전체 활동 현황 | 점검계정·계정별기록·업무별현황·점검이력 시트 추가 |

## 단계별 사용법

1. **설치와 범위 지정**: Burp Extensions에서 이전 Workbench를 해제하고 `burp-workbench-kr-0.21.0.jar`를 Java 확장으로 로드합니다. 트래픽 우클릭 → SCOPE 지정으로 허가받은 범위를 설정합니다.
2. **점검 계정 등록**: 활동 추적 → 계정별 점검 → 계정 등록에서 `Alice`, `Bob`, `Admin` 등의 이름과 Origin·역할·조직을 등록합니다. 예: Origin `https://test.example`, 역할 `USER`, 조직 `A`. 쿠키나 토큰을 이름/설명 칸에 입력하지 마세요. 비로그인도 명시적으로 등록할 수 있습니다.
3. **세션 연결**: 권한 비교에서 실제 로그인 트래픽의 인증 후보를 슬롯에 배정합니다. **세션·권한 매트릭스 → 점검 이력 계정**에서 해당 이름을 선택합니다. **이 슬롯을 새 점검 계정으로 등록**으로 바로 등록할 수도 있습니다. 슬롯을 다른 세션으로 바꾸면 점검 계정 연결을 다시 지정하세요.
4. **트래픽에서 연결하는 방법**: 트래픽에서 1~20개 요청을 선택한 뒤 활동 추적 → 계정별 점검에서 계정을 고르고 **선택 트래픽 연결**을 누릅니다. 같은 Origin/SCOPE와 인증 조건을 검증합니다. 하나의 동일한 인증 조건을 서로 다른 계정에 연결하면 거부합니다. 인증 후보 식별 쿠키 이름 설정을 사용하면 세션 쿠키와 화면 환경설정 쿠키를 구분할 수 있습니다.
5. **계정별 누락 확인**: 계정별 점검에서 계정을 바꾸고 `미점검` 또는 `재검토 필요` 필터를 선택합니다. 해당 Origin에서 발견된 메서드별 API를 표시하므로 아직 그 계정으로 방문하지 않은 URL도 확인할 수 있습니다. `트래픽 관측`, `검사 시도`, `저장 증거`, `미완료 입력`을 함께 확인합니다.
6. **검사와 완료 구분**: 권한 비교 결과가 연결된 계정의 검사 시도/최근 결과에 반영됩니다. 실제 요청을 보내지 못한 세션 갱신 실패도 검사 시도와 재검토 근거로 기록되므로, 이 숫자는 네트워크 전송 건수가 아닙니다. 결과를 사람이 확인한 뒤 **선택 URL 완료**를 누릅니다. 입력별 검사는 오른쪽 입력 목록에서 **입력 완료 / 해제**로 따로 표시합니다.
7. **업무 등록**: 활동 추적 → 업무별 현황 → **업무 등록**에서 업무 이름/설명을 입력하고 요구 계정을 Ctrl/Shift로 선택합니다. 필요하면 **완료 전 업무에 연결된 증거 ZIP 1개 이상**을 선택합니다.
8. **API 연결**: 계정별 점검에서 API를 선택해 **선택 API → 업무**를 누르고, 새 창의 메서드/URL 미리보기를 확인해 **업무에 추가**합니다. 업무별 현황의 아래 상세 API에서도 같은 동작을 사용할 수 있습니다. 창을 연 시점의 대상이 유지됩니다. GET/POST는 별도 대상이며 최대 32개입니다. API와 다른 Origin의 계정은 요구 조합에서 제외하므로 상세 목록의 계정 × API를 반드시 확인하세요.
9. **증거 저장**: 권한 비교/업무 흐름/페이로드 등의 결과를 점검 지원으로 전달한 뒤 증거 ZIP을 저장합니다. 준비 목록에 넣는 것만으로 저장 건수가 증가하지 않습니다. 연결 계정이 있고 실제 ZIP 쓰기에 성공한 항목만 현황에 연결합니다. 비교 ZIP은 계정 ID를 유지하며 알려진 인증값을 가립니다. 메타데이터 연결 오류는 파일 저장 성공과 별도로 표시됩니다.
10. **업무 완료**: 모든 요구 조합의 URL을 수동 완료하고 재검토 사유를 해소하면 `완료 준비`가 표시됩니다. 증거 조건을 켰다면 연결 ZIP이 1개 이상 있어야 합니다. 마지막으로 **업무 완료**를 눌러 마감합니다. 자동 검사나 준비 상태가 업무 완료를 대신하지 않습니다.
11. **재점검**: 완료 후 새 입력, 관련 검사 오류/갱신 실패, 계정 완료 해제, 새 업무 API가 생기면 `재검토 필요`로 돌아갑니다. 계정 URL을 재완료해도 이전 업무 재검토 표시는 유지되므로, 업무 전체를 다시 확인하고 **업무 완료**를 명시적으로 누릅니다.
12. **이력·저장**: **점검 이력**으로 최근 작업을 확인하고 활동 추적의 JSON 저장/불러오기와 Excel 내보내기를 사용합니다. 계정 ID·역할·완료·업무·저장 증거 기록은 복원됩니다. 쿠키/토큰과 세션 연결은 저장되지 않아 재시작/불러오기 후 다시 연결해야 합니다. 계정 이름/역할 변경은 같은 ID의 이력을 유지합니다.

## 제가 전체 점검을 시작한다면

허가받은 커뮤니티 실습 사이트에서 Alice/Bob/Admin과 비로그인 계정을 등록하고, 두 일반 계정은 다른 조직/소유 게시글을 준비합니다. 우선 SCOPE를 지정하고 각 계정으로 로그인·게시글 목록·상세·검색·첨부·관리 메뉴를 정상 사용해 트래픽을 수집합니다.

JS 추출과 URL 수집으로 숨은 API와 메서드를 찾고 미확정 JS 주소는 근거를 확인한 뒤 확정합니다. 환경 탐색에서는 허용된 경로와 선택 계정별 응답을 확인합니다. Passive 결과는 보안 헤더·오류 노출·민감정보 등 후보로 분류하고, 데이터 차이에서 응답 필드/접근 차이를 확인합니다.

업무별 현황에는 `로그인·세션`, `게시글 관리`, `첨부파일`, `검색`, `관리 기능`을 등록합니다. 예를 들어 게시글 관리는 GET 목록·GET 상세·POST 생성 등 실제 발견한 API를 연결하고 Alice/Bob/Admin을 요구 계정으로 지정합니다. 계정별 점검의 미점검 필터를 통해 같은 기능을 다른 계정에서 놓쳤는지 확인합니다.

권한 비교에서는 소유자/타인/관리자의 허용·거부 기대 정책을 먼저 정하고 교차 접근을 확인합니다. 업무 흐름으로 정상 생성→조회→수정→삭제와 단계별 기대 결과를 확인합니다. 입력별로 필요하고 허가된 페이로드 검사를 수행하고, 외부 콜백은 승인된 환경에서만 검증합니다. 단순 반사/동일 응답만으로 취약점을 확정하지 않고 대조 요청과 실제 영향으로 재현합니다.

확인한 결과를 증거 ZIP으로 저장한 뒤 계정별 URL/입력 완료를 표시하고 업무별 요구 조합을 마감합니다. 마지막에는 재검토 필요·미점검·증거 저장 필요 항목을 확인하고 JSON/Excel을 남깁니다. 이 목록은 점검 누락을 줄이는 관리 수단이며 취약점 존재/부재를 자동으로 보증하지 않습니다.

## 완료 의미와 현재 한도

- 계정의 신원은 진단자가 확인해 연결합니다. 확장이 로그인 사용자/역할을 자동으로 증명하지 않습니다. 동일 세션 값으로 다른 사용자가 로그인하거나 권한이 바뀌면 연결 해제 후 다시 확인·연결하세요.
- URL 완료와 입력 완료는 별도입니다. 업무 완료 조건은 같은 Origin의 요구 계정/API URL 수동 완료와 재검토 여부이며, 모든 입력의 개별 완료를 강제하지 않습니다.
- 선택적 증거 조건은 업무에 연결된 성공 저장 ZIP **1개 이상**입니다. 모든 계정/API에 대한 증거를 요구하거나 파일이 현재 존재하는지 확인하는 조건은 아닙니다.
- 계정 최대 16개, 업무 최대 1,000개, 업무별 API 최대 32개, 계정별 API 기록 최대 10,000개, 입력 기록 최대 50,000개, 최근 이력 최대 5,000개, 메모리 세션 연결 최대 512개, 증거 참조 최대 1,000개입니다. 계정 삭제와 계정별 입력 값 변화 해시, 자동 로그인 주체 판별은 아직 제공하지 않습니다.
- 메타데이터에는 세션 인증값/요청 본문을 저장하지 않습니다. 직접 입력한 이름/메모에는 민감한 내용을 적지 마세요. 실제 증거에는 선택 옵션에 따른 가림된 요청·응답 내용이 포함됩니다.
- 기존 0.19 PDF는 기본 기능의 과거 가이드입니다. 새 탭과 사용법은 이 문서를 우선하며, 이번 배포에서 PDF를 수정하지 않았습니다.

## 검증 결과

- 단위/API 어댑터/헤드리스 화면 제어: **905개, 31개 테스트 묶음**. 새 계정·업무 회귀 검사 57개 포함.
- 페이로드 HTTP 실습 검사: **127개**.
- 전체 기능 HTTP 실습: **100개 검사, 실제 요청 199건**, 16개 페이로드 프로필 포함.
- 실제 Burp Community **2026.7.3-52685**에 최종 JAR 로드: **180개** 검사. 기존 기능 158개와 새 계정/업무 22개. 실제 404/200 비교, 세 계정 분리, 증거 ZIP, 완료 후 새 입력, 저장·복원, 세션 갱신 실패를 검증했습니다.
- 총 **1312개 검사 통과**, 확장 오류 로그 0바이트. 임시 서버/프록시/콜백 포트 종료 확인.

클라우드 VM이 아닌 격리된 로컬 헤드리스 Burp와 임시 프로필을 사용했습니다. 사용자 화면/기존 프록시 설정은 변경하지 않았습니다. 실제 브라우저 JS/DOM, Pro Collaborator 서비스, 외부 BApp, TLS/HTTP2와 전체 Docker/Oracle/Nginx 구성은 검증 완료로 표시하지 않습니다. 검사 통과가 모든 버그의 부재를 보증하지는 않습니다.
