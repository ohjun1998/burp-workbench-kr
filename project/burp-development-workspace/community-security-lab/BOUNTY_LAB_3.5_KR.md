# 커뮤니티 사이트 3.5 — 버그바운티 흐름 실습

실행 후 `/bounty-lab`을 엽니다. 기존 커뮤니티와 전 기능 검증 페이지에서 연결됩니다. 신규 화면은 쓰기 요청을 자동 실행하지 않으며, 사용자가 누른 요청의 상태·헤더·본문을 문자열로 표시합니다. `/api/bounty/manifest`에는 기대 정책, API 흐름, 제한을 기계 판독 가능한 JSON으로 제공합니다.

## 계정과 정책

기존 실습 계정의 비밀번호는 `LabOnly!2026`입니다. Alice와 Moderator는 조직 A, Bob은 조직 B, Admin은 전체 관리자입니다. 계정명/조직 표기는 이 실습의 정해진 기대값이며 실제 서비스에서 역할을 증명하는 방식은 아닙니다.

`GET /api/bounty/{mode}/objects/{id}`의 `mode`는 `vuln` 또는 `fixed`입니다.

| ID | 정책 | fixed에서 읽을 수 있는 계정 |
|---|---|---|
| 201 | PUBLIC | 비회원 포함 전체 |
| 202 | OWNER_ONLY / Bob | Bob, Admin |
| 203 | TENANT / 조직 A | Alice, Moderator, Admin |
| 204 | SHARED | Alice, Bob, Admin |
| 205 | TENANT / 조직 B | Bob, Admin |
| 206 | OWNER_ONLY / Alice | Alice, Admin |

성공은 모두 HTTP 200, 거부·없는 객체는 모두 HTTP 404입니다. `vuln`은 로그인한 계정이 모든 객체를 읽을 수 있도록 의도적으로 권한 검사를 빠뜨렸습니다. URL 형태와 상태만 같다고 같은 권한 정책으로 축약하지 마세요.

권한 비교 예:

1. Bob 세션으로 fixed 객체 202와 205를 수집하고, Alice 세션을 비교 슬롯에 연결합니다.
2. 이 두 경로의 Alice 기대값은 DENY로 지정합니다. 다른 슬롯 기대값은 실제 계정/정책에 맞춥니다.
3. Alice의 404를 소유자 Bob의 동일 객체 재조회와 함께 확인합니다. 소유자도 404이거나 본문이 변했다면 차단 확정 대신 존재·세션을 재검토합니다.
4. vuln의 같은 객체에서 Alice가 200 및 같은 자료를 읽는지 대조합니다.
5. 객체 203, 204, 201도 각각 확인하여 조직·공유·공개 접근이 오탐으로 분류되지 않게 합니다.

## 저장형 출력의 단계별 확인

1. 버그바운티 지원 → 저장/조회 연결에서 `PR_0123456789abcdef`처럼 고유한 마커를 등록합니다.
2. `POST /api/bounty/{mode}/stored`에 form 본문 `value=<b>PR_0123456789abcdef</b>`를 보냅니다. 실제 HTTP에서는 URL 인코딩합니다.
3. 생성 응답의 `url`을 GET으로 조회합니다. 성공한 쓰기 응답만으로 서버 저장이나 XSS 실행을 확정하지 않습니다.
4. vuln은 HTML 태그를 그대로 반환하고 fixed는 `&lt;b&gt;...`로 표시합니다. 확장은 쓰기 성공, 조회 재출력, HTML 출력, 브라우저 수동 확인을 따로 나타냅니다.
5. 실제 브라우저에서 실행을 확인한 경우에만 확인용 이미지 파일을 연결합니다. 마커를 보는 것과 스크립트 실행을 입증하는 것은 다릅니다. 단순 `<b>` 마커 자체는 실행 페이로드가 아닙니다.

fixed의 모든 신규 쓰기에는 로그인 응답의 `csrf` 값을 `X-CSRF-Token` 헤더로 넣습니다. 신규 stored 데이터는 fixed에서 소유자만 읽을 수 있습니다. vuln은 생성 주소를 아는 다른 계정/비회원도 읽을 수 있어, 출력 처리와 객체 접근을 독립적으로 대조할 수 있습니다.

## 업로드·다운로드 대조

- `POST /api/bounty/vuln/uploads?name=probe.html`에 `Content-Type: text/html`과 마커 HTML 본문을 보냅니다. 반환된 `url`은 HTML/inline으로 응답합니다.
- fixed는 이름이 `.txt`로 끝나는 파일만 수락하고 응답을 `text/plain`/attachment + `nosniff`로 제공합니다. `.html` 이름은 HTTP 415입니다.
- fixed 다운로드는 소유자만 허용하고 다른 계정/비회원은 404입니다. vuln 다운로드는 주소를 아는 사용자에게 공개됩니다.
- 파일명은 실습 메타데이터입니다. 서버 파일시스템 경로로 사용하지 않으며 데이터는 메모리에만 둡니다.

## 정리와 제한

`POST /api/bounty/reset`은 로그인 및 CSRF 토큰을 요구하며 현재 계정이 새 `/api/bounty/` 기능에서 만든 데이터만 제거합니다. 기존 커뮤니티 게시글·첨부와 다른 계정 데이터는 유지합니다. 개별 데이터는 반환된 URL 뒤에 `/delete`를 붙인 POST로 삭제하며, 모든 모드에서 소유자와 CSRF를 확인합니다.

- 계정당 64개, 전체 256개, 파일당 1~65,536바이트, 저장 본문 4,096문자 제한.
- 초과 생성은 429, 너무 큰 파일/본문은 400입니다.
- 서버 재시작 시 신규 bounty 데이터는 사라집니다. 기존 커뮤니티 DB 데이터를 초기화하는 기능이 아닙니다.
- 로컬 loopback 실습 환경에서만 사용합니다. 취약 모드를 외부에 공개하지 않습니다.

## 재현 가능한 검증

저장소 루트에서 `python dev.py check`를 실행합니다. 신규 감사 하네스는 현재 릴리스 JAR와 현재 lab Java 소스를 사용해 새 격리 서버에서 권한/정책, 저장·조회, 업로드, 한도, 초기화, 실제 SQL/XSS 대조 및 증거 내보내기를 검사합니다. 개별 실행은 다음과 같습니다.

```sh
python audit/0.23.0/run_audit.py --workspace . --port 18399
```

기존 HTTP 검사로 준비된 런타임 의존성의 SHA-256을 모두 확인하고 실행합니다. 결과는 `audit/0.23.0/.run/`에 생성됩니다. 실제 Burp 호스트, 브라우저 DOM/JavaScript 실행, Docker/Oracle/Nginx 전체 스택을 수행했다고 해석하지 마세요. 그 환경들은 별도 실행 근거가 필요합니다.
